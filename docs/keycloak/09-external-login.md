# Вход через Госуслуги и Яндекс ID

**Статус:** ✅ готово на заглушке, настоящих ключей нет · **Задача:** [#55](https://github.com/123kapefa/auth-service-sandbox/issues/55)
(вместо Google и GitHub — Госуслуги и Яндекс ID)

## Цель

Дать войти через Госуслуги и Яндекс ID так же, как по телефону: тот же аккаунт, те же роли и cookie сервиса. Ключей
Яндекса и Госуслуг (ЕСИА) у песочницы нет, поэтому весь путь проверен на заглушке, которая ведёт себя, как
настоящие сервисы, в той части, которую видит Keycloak. Включить по-настоящему — подставить ключи
([«Как включить по-настоящему»](#как-включить-по-настоящему)).

| Что | Как |
|---|---|
| Кнопки | на странице входа под формой: «Или войдите через» — **Госуслуги**, **Яндекс ID** |
| Новый человек | новая учётная запись; логин — телефон цифрами, как у всех (`79990000101`), атрибут `phone`, почта подтверждена |
| Телефон или почта уже есть | «Аккаунт уже есть — привязать?» → пароль **от этой** учётной записи → привязано; дальше вход сразу |
| Что берём у провайдера | только подтверждённое: у ЕСИА — контакты с `vrfStu = VERIFIED`, у Яндекса — `default_phone`, `default_email` |
| Без телефона | логин `yandex-<id>` / `esia-<oid>`, по почте — как выше |
| 2FA | у кого включена — после внешнего входа спрашивается код (и при привязке — один раз) |
| Доступ к приложению закрыт | «Доступ закрыт», как после пароля: внешний вход проверку не обходит |
| Отказ у провайдера | снова форма входа |

## Как выглядит

1. Форма входа: телефон или почта, пароль, «Войти по коду», ниже — «Или войдите через»: Госуслуги, Яндекс ID.
2. Кнопка → страница Госуслуг или Яндекса (в песочнице — заглушка «войти как»: тестовые люди и «Отказаться»).
3. Новый человек — сразу в приложение. Уже есть аккаунт с этим телефоном или почтой — «Привязать?» → форма «только
   пароль» (логин известен; без «Войти по коду» и кнопок провайдеров) → 2FA, если включена → в приложение.

## Как устроено

### Провайдеры (плагин `infra/keycloak/providers/code-login`)

| Провайдер | Класс | Протокол |
|---|---|---|
| `yandex` — Яндекс ID | `YandexIdentityProvider` | OAuth 2.0: код → токен (`client_secret` в теле) → `login.yandex.ru/info` с `Authorization: OAuth <токен>`; доступы `login:info login:email login:default_phone` |
| `esia` — Госуслуги | `EsiaIdentityProvider` | OAuth 2.0 ЕСИА: `/aas/oauth2/v2/ac` и `/aas/oauth2/v3/te`; данные — REST `/rs/prns/{oid}` и `/rs/prns/{oid}/ctts` |

Обоих Keycloak показывает в админке среди соцсетей. Адреса по умолчанию — настоящие, в настройках провайдера их
можно переопределить (так песочница ходит в заглушку).

**Чем ЕСИА отличается от обычного OAuth** (`EsiaRequest`, всё покрыто юнит-тестами):

- вместо секрета — **подпись каждого запроса** по ГОСТ Р 34.10-2012 ключом сертификата системы: `client_secret` —
  открепленная подпись строки `client_id + scope + timestamp + state + redirect_uri` (для обмена кода — `+ code`),
  base64 url-safe;
- в запросе ещё `timestamp` (`yyyy.MM.dd HH:mm:ss +0300`), `access_type=online` и `client_certificate_hash`;
- `state` — UUID. Свой `state` Keycloak (длинный) хранится на время входа под этим UUID и подставляется обратно,
  когда ЕСИА возвращает браузер (один раз — повтор того же ответа не пройдёт);
- `oid` человека — из access-токена (`urn:esia:sbj_id`), имя и контакты — отдельными запросами.

Подписать по ГОСТ внутри Keycloak нельзя (нужна сертифицированная криптография), и ключ системы лучше держать
отдельно. Поэтому подписывает **сервис подписи** (`EsiaSigner`): `POST <signerUrl>`, тело — текст, ответ — подпись PKCS#7
в base64. В песочнице подписывает заглушка; по-настоящему — свой небольшой сервис на КриптоПро CSP (или КриптоПро DSS)
с ключом системы.

### Сценарии входа (realm)

```
platform first external login        первый вход через провайдера
├── Review Profile                   REQUIRED     только если чего-то обязательного не хватает
└── platform create or link          REQUIRED
    ├── Create User If Unique        ALTERNATIVE  нет такого логина (телефона) и почты → новая учётная запись
    └── platform link existing       ALTERNATIVE
        ├── Confirm link             REQUIRED     «Аккаунт уже есть — привязать?»
        └── platform-link-password   REQUIRED     пароль от найденной учётной записи  ← плагин

platform after external login        после каждого входа через провайдера
├── platform external 2FA            CONDITIONAL  2FA, если включена (как platform conditional 2FA)
└── platform-app-access-check        REQUIRED     доступ к приложению  ← плагин
```

- **Привязка — паролем от найденной учётной записи** (`LinkPasswordForm`). Встроенная форма Keycloak показывает поле
  логина и даёт вписать другой аккаунт; наша знает учётную запись заранее и просит только пароль.
- **Почему отдельный сценарий «после входа».** Вход через провайдера не проходит шаги `platform browser` после
  `identity-provider-redirector`: без него внешний вход обходил бы и 2FA, и «Доступ закрыт».
- 2FA при привязке спрашивается один раз — в «после входа» (в первом входе её нет).

### Заглушка (`infra/idp-stub/stub.py`, сервис `idp-stub` в `compose.yaml`)

Python без зависимостей в образе `python:3.13-alpine`, порт `8190`. Яндекс ID (`/yandex/...`), ЕСИА (`/esia/...`) и
сервис подписи (`/sign`, HMAC вместо ГОСТ). Заглушка **проверяет** то же, что проверяет ЕСИА: `client_id`, `state` —
UUID, формат `timestamp`, `client_certificate_hash` и подпись — у запроса кода и у обмена кода; Яндекс — `client_secret`
и заголовок `Authorization: OAuth`. Тестовые люди — в начале файла: новые (телефоны `7999000010x`), с телефоном
покупателя `79990000001` и пользователя с 2FA `79990000006`, без телефона, с неподтверждённым номером.

Адреса и ключи — переменные `ESIA_*` и `YANDEX_*` (`compose.yaml` → `keycloak`, подставляются в realm при импорте);
не заданы — заглушка.

## Как включить по-настоящему

Адрес возврата (Redirect URI) у обоих — публичный адрес Keycloak + `/realms/<проект>/broker/<yandex|esia>/endpoint`.

**Яндекс ID** — бесплатно, за час:

1. На [oauth.yandex.ru](https://oauth.yandex.ru) создать приложение «Веб-сервисы», указать Redirect URI.
2. Доступы: «Доступ к логину, имени и фамилии, полу», «Доступ к адресу электронной почты», «Доступ к номеру телефона».
3. ClientID и Client secret → `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`; адреса — настоящие (в `.env.example`).

**Госуслуги (ЕСИА)** — только для юрлица или ИП, недели:

1. Зарегистрировать информационную систему в ЕСИА (заявка через технологический портал Минцифры): получить
   мнемонику системы — это `ESIA_CLIENT_ID`; запросить доступы `openid fullname email mobile`; указать Redirect URI.
2. Получить квалифицированный сертификат ЭП для системы (ГОСТ Р 34.10-2012) и зарегистрировать его в ЕСИА.
3. Поднять сервис подписи с этим ключом (КриптоПро CSP или DSS) по контракту выше → `ESIA_SIGNER_URL`.
4. Посчитать хэш сертификата утилитой ЕСИА → `ESIA_CERTIFICATE_HASH`.
5. Сначала — тестовая среда `https://esia-portal1.test.gosuslugi.ru` (адреса и `ESIA_API_URL`), потом бой.

Затем — `.env` (или окружение) и `scripts/project/enable-external-login.py <проект>` (или для песочницы — пересоздать
realm). Формат подписываемой строки и параметров взят из методических рекомендаций ЕСИА — при подключении сверить
с их актуальной версией: всё это в одном классе `EsiaRequest`.

## Ограничения и что дальше

- **Привязка — только паролем.** Кто входит только по коду (без пароля), привязать не сможет: сначала «Забыли пароль».
  Подтверждение кодом из SMS — возможное продолжение (шаг плагина вместо `platform-link-password`).
- **Отвязать вход** пока можно только в админке Keycloak (пользователь → Identity provider links); в своём кабинете и
  админке — нет.
- **Данные не обновляются** после первого входа (`syncMode: IMPORT`): сменил почту в Яндексе — у нас прежняя.
- **Подпись ответов ЕСИА не проверяется**: токен Keycloak получает напрямую от ЕСИА по TLS. Проверка ГОСТ-подписи
  токена — задача того же сервиса подписи, если понадобится.
- Удалённого в админке провайдера Keycloak какое-то время помнит в кэше привязок пользователей: после удаления
  провайдера — перезапуск Keycloak.
