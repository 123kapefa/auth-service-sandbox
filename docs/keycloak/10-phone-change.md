# Этап 10.5. Смена номера самим человеком

**Статус:** ✅ готово (логика; кнопка в кабинете — 10.9, оформление — 10.8) · **Задача:** [#133](https://github.com/123kapefa/auth-service-sandbox/issues/133) (этап 10 — [#128](https://github.com/123kapefa/auth-service-sandbox/issues/128))

Человек меняет номер сам, без админа, так же, как почту: из кабинета на страницу Keycloak, ввести новый номер,
подтвердить кодом, пришедшим на него. После смены код на старый номер этот аккаунт больше не открывает.

## Как выглядит

1. Кабинет → «Сменить номер» (сейчас — ссылка `/auth/login?return_to=/account/&action=update-phone`; кнопка — 10.9).
   Если человек входил больше 5 минут назад, Keycloak сначала просит войти заново.
2. **Новый номер**: на странице нынешний номер (`Сейчас: +7…`) и поле нового. «Получить код» или «Отмена».
   - не номер — «Введите номер телефона, например +7 999 000-00-01.»;
   - тот же номер — «Это ваш нынешний номер.»;
   - номер другого аккаунта — «Этот номер уже привязан к другому аккаунту. Если это ваш номер, напишите в поддержку.»;
   - номер меняли меньше суток назад — «Номер можно менять раз в сутки» и через сколько часов; поля нет, только «Отмена».
3. **Код** — тот же экран, что при входе по коду: звонок (код — последние 4 цифры номера), «Отправить ещё раз»,
   «Получить SMS»; плюс «Другой номер». Те же лимиты и пауза перед повтором (10.1), но свои коды: код входа на этот
   номер для смены не годится.
4. Верный код → номер изменён, человек возвращается в кабинет (`action_status=success`).

## Что меняется

- Атрибут `phone` — новый номер; `phone_previous` — прежний, `phone_changed_at` — когда (для «раз в сутки»).
- Логин — новый номер, если логином был старый номер (у покупателей так всегда). Пароль, ключи доступа,
  приложение-аутентификатор, почта, роли — без изменений.
- Письмо на почту «Номер телефона изменён» (новый номер скрыт частично) и SMS на старый номер: к аккаунту привязан
  другой номер, если это не вы — в поддержку.
- Журнал Keycloak — событие `CUSTOM_REQUIRED_ACTION` (`platform-update-phone`) с `previous_phone` и `updated_phone`; журнал сервиса —
  `UserPhoneChanged` (`{phone: {old, new}}`, сделал сам человек). Запись в журнал сервиса — когда человек вернулся
  после смены (одна, даже если вернулся дважды).
- Код на старый номер дальше работает как на любой незнакомый номер: создаёт новый аккаунт покупателя, но не открывает
  этот.

## Как устроено

- Плагин: обязательное действие `platform-update-phone` (`UpdatePhoneAction`, запускается через `kc_action`,
  `getMaxAuthAge` — 300 с). Правила — `PhoneChangeRules` (без Keycloak, с тестами): раз в сутки → не номер → тот же →
  занят.
- Отправка и проверка кодов вынесены из входа по коду в `CodeDispatcher` — ими пользуются и вход, и смена номера;
  коды смены лежат отдельно (`platform-phone-change:<номер>`).
- Письма и SMS «это были вы?» — общий `AccountNotices` (им же пользуются уведомления о способах входа, 10.3).
- Тема: страница `platform-update-phone.ftl` (`UpdatePhone.tsx`), шаг кода — компонент экрана кода входа.
- Сервис: `action=update-phone` → `kc_action=platform-update-phone`; на возврате — `PhoneChangeRecorder`.

## Старый стенд

Realm импортируется только в пустую базу, поэтому на стенде, поднятом до 10.5:

```bash
docker compose up -d --build --wait keycloak auth-service   # новый плагин, тема, сервис
python3 scripts/project/enable-phone-change.py sandbox      # включить действие в realm
```

## Что дальше

- Кнопка «Сменить номер» в кабинете (10.9) и оформление страницы (10.8).
- Админ видит смену номера в журнале; сменить номер за человека — по-прежнему в админке Keycloak.

## Проверка

```bash
scripts/keycloak/check-phone-change.sh
```

Ожидается `Итого: 27 ✓, 0 ✗`: страница сразу после входа; не номер, тот же, занятый — отказ; звонок на новый номер,
неверный код, «Другой номер», код входа не годится; верный код — номер, логин и прежний номер записаны, письмо и SMS
на старый номер, одна запись в журнале сервиса; вход кодом и паролем по новому номеру, код на старый — другой аккаунт;
повторная смена в тот же день — отказ, «Отмена».
