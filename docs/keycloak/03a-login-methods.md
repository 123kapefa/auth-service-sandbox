# Этап 3а. Способы входа

**Статус:** ✅ готово · **Ветка:** `stage-3a/login-methods`

## Цель

На странице входа Keycloak — способы входа платформы, а пользователь сам решает, что ещё включить:

| Способ | Как входит пользователь |
|---|---|
| Пароль | логин — **телефон или почта** |
| Сброс пароля | «Забыли пароль?» → письмо со ссылкой → новый пароль → сразу вход |
| 2FA — по желанию | после пароля — код из приложения-аутентификатора (или одноразовый код восстановления) |
| Ключ доступа (passkey) | без пароля: отпечаток пальца, лицо или PIN-код устройства |

Вход по коду из SMS или письма — этап 5 (нужен свой Java-плагин). Самостоятельная регистрация пока выключена.

Почти всё — настройкой realm, без кода сервиса. Сервис добавил только ссылку `GET /auth/account` в
личный кабинет и кнопку «Настройки входа» на демо-странице. _(До этапа 6б ссылка вела в кабинет Keycloak; с 6б — в
свой кабинет `/account/`, кнопка — «Личный кабинет», 2FA и ключ доступа — карточка «Безопасность» в нём, см.
[06b-account-branding.md](06b-account-branding.md).)_

## Что настроено

### Телефон или почта

- `loginWithEmailAllowed: true`, `duplicateEmailsAllowed: false` (одна почта — один пользователь).
- Логин-телефон хранится **цифрами без «+»** (`79990000001`); у тестовых пользователей — подтверждённая почта `*@sandbox.test`.
- Подпись поля — «Телефон или почта» (`localizationTexts`).
- **Тема входа `sandbox`** (`infra/keycloak/themes/sandbox`) _(до этапа 4в; с 4в тема — `login-theme/` на React)_: наследует `keycloak.v2`, шаблоны не копирует, добавляет
  `phone-login.js` — при вводе номера показывает «+», почту не трогает, перед отправкой приводит номер к цифрам
  (`+7 (999) 000-00-01` → `79990000001`). Работает и на странице «Забыли пароль?».

### Сброс пароля

- `resetPasswordAllowed: true`, SMTP → Mailpit (`mailpit:1025`, `no-reply@sandbox.test`). Письма — http://localhost:8025.
- Ссылка одноразовая. Для неизвестного логина — тот же ответ и без письма: по форме нельзя узнать, есть ли пользователь.

### 2FA по желанию

Свой сценарий входа **`sandbox browser`** (копия встроенного `browser`; встроенные лучше не править), назначен `browserFlow`:

```
sandbox browser
├── cookie (уже вошёл)                  ALTERNATIVE
├── вход через внешнего провайдера      ALTERNATIVE
└── sandbox forms                       ALTERNATIVE
    ├── логин и пароль                  REQUIRED
    └── sandbox conditional 2FA         CONDITIONAL
        ├── условие: пользователь настроил 2FA          REQUIRED
        ├── условие: вошёл не по passkey                REQUIRED
        ├── код из приложения (OTP)                     ALTERNATIVE
        └── код восстановления                          ALTERNATIVE   ← во встроенном выключен
```

Пользователь включает 2FA сам в личном кабинете: «Настроить приложение аутентификатор», «Настроить коды восстановления».

### Ключ доступа (passkey)

- `webAuthnPolicyPasswordlessPasskeysEnabled: true` — кнопка «Войти с ключом доступа» и подсказка браузера в поле
  логина (`autocomplete="username webauthn"`).
- Создаётся в личном кабинете: «Без пароля → Настроить Ключ доступа».

### Личный кабинет Keycloak

`http://localhost:8180/realms/sandbox/account` (или «Личный кабинет» на демо-странице → «Безопасность») → «Вход»: пароль, 2FA, ключ доступа.

## Как проверить

```bash
docker compose up -d --wait keycloak mailpit auth-service
```

```bash
scripts/keycloak/check-login-methods.sh
```

Ожидается `Итого: 14 ✓, 0 ✗`: вход по почте, сброс пароля целиком (письмо, ссылка, новый пароль, вход,
одноразовость ссылки, неизвестный логин), 2FA (без неё код не спрашивают; неверный код отклонён; верный — вход;
код считает сам скрипт по TOTP). `check-stand.sh` — 28 ✓ (подпись поля, тема, «Забыли пароль?», кнопка passkey,
нет неверного перевода, нет `resource_access` в токенах наших клиентов).

**Руками — ключ доступа** (скриптом не пройти, нужен настоящий аутентификатор; Chrome или Safari):

1. http://localhost:8080 → «Войти» → `79990000003` / `Test1234!` → «Личный кабинет» → «Безопасность» → «Без пароля → Настроить Ключ доступа» → Touch ID.
2. Выйти → «Войти» → «Войти с ключом доступа» (или нажать на поле логина — браузер предложит ключ) → Touch ID.

Если нажать «Войти с ключом доступа» до создания ключа, macOS ответит «нет сохранённых ключей для этого сайта» и
предложит QR-код или аппаратный ключ — это не ошибка.

## Грабли

- **Перевод passkey.** В стандартном ru-переводе Keycloak 26.4 passkey назван «паролем»: «Используйте свой пароль
  для входа без пароля», кнопка «Войти с помощью пароля» запускает вход по passkey. 18 строк переопределены в
  `localizationTexts` на «ключ доступа». `check-stand.sh` проверяет, что старого текста на странице нет.
- **Личный кабинет не открывался (401).** Realm объявляет свои client scopes, поэтому встроенных (`roles` и др.)
  нет, и токен кабинета не проходил API кабинета. Решение: scope `account-access` (роли клиентов в токене),
  клиенты `account` и `account-console` описаны в JSON явно, тестовым пользователям — роль `default-roles-sandbox`.
  Не сработало: (1) описать только `account-console` — Keycloak сам создаёт его, если нет `account`, импорт падает
  на дубле; (2) добавить scope в значения по умолчанию realm — встроенные клиенты создаются **до** импорта scopes
  и остаются без них.
- **Свои сценарии входа и встроенные.** Если в realm JSON есть `authenticationFlows`, встроенные сценарии всё равно
  создаются — кроме `saml ecp` (у нас SAML нет).
- **Кэш ключей после пересоздания стенда.** Сервис обновляет ключи подписи Keycloak не чаще раза в 5 минут;
  после нескольких пересозданий подряд все токены получают 401 — нужен `docker compose restart auth-service`.
- **Секрет OTP в realm — «сырая» строка**, а приложения-аутентификаторы принимают Base32. Для ручной проверки —
  значение из таблицы выше.
- **Тема в проде** монтируется папкой только на стенде; в проде её нужно встроить в образ Keycloak.
