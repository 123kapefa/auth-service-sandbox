# Этап 4. Режимы, API администрирования, события, мгновенный отзыв

**Статус:** ✅ готово · **Ветка:** `stage-4/admin` · **Задача:** [#42](https://github.com/123kapefa/auth-service-sandbox/issues/42)

## Цель

Серверная часть администрирования — основа для своей админки (этап 4б) и динамических ролей (4а):
переключение режима, пользователи, блокировка, роли, доступ к приложению, сессии, журнал — и **мгновенный отзыв**
уже выданных токенов (раньше отозванный access-токен жил до 15 минут).

Термины: **проект** — отдельный продукт со своей базой людей (realm), **приложение** — сайт или программа внутри
проекта (клиент). Действия делятся на уровень **аккаунта** (блокировка, роль, «выйти везде» — весь проект) и уровень
**приложения** (закрыть доступ к одному приложению).

## API

Пути — как в боевом сервисе, ответы — в `Envelope` (стандарт платформы), ошибки — с кодами.

| Метод и путь | Право | Что делает |
|---|---|---|
| `POST /auth/mode { activeMode }` | вошёл | переключить режим; недоступный — 403 `auth.mode.not_available` |
| `GET /auth/admin/users?search&page&pageSize` | `users.view` | пользователи: поиск по телефону («как набрали»), почте, логину; страницы, `hasMore` |
| `GET /auth/admin/users/{id}` | `users.view` | карточка: роль, режимы, блокировка, пароль, последний вход |
| `PUT /auth/admin/users/{id}/restriction { restricted, reason }` | `users.block` | заблокировать аккаунт или разблокировать |
| `PUT /auth/admin/users/{id}/role { role }` | `users.roles.manage` | сменить роль (customer, manager, admin) |
| `GET /auth/admin/users/{id}/apps` | `users.view` | приложения проекта и доступ к ним |
| `PUT /auth/admin/users/{id}/apps/{clientId}/access { hasAccess }` | `users.block` | открыть или закрыть доступ к приложению |
| `GET /auth/admin/users/{id}/sessions` | `users.view` | сессии пользователя |
| `POST /auth/admin/users/{id}/logout` | `users.sessions.manage` | «выйти везде» |
| `GET /security/sessions` | вошёл | свои сессии, текущая — `isCurrent` |
| `POST /security/sessions/{id}/terminate` | вошёл | завершить свою сессию (чужая — 404) |
| `POST /security/sessions/terminate-all-others` | вошёл | завершить все, кроме текущей |
| `GET /auth/admin/audit?objectId&actorId&action&from&to&page&pageSize` | `audit.view` | журнал действий сотрудников |
| `GET /auth/admin/login-events?userId&page&pageSize` | `audit.view` | входы, ошибки входа, выходы (события Keycloak) |
| `GET /auth/login?reauth=true` | — | войти заново (`prompt=login`): пароль и 2FA, если включена |
| `POST /auth/backchannel-logout` | подпись `logout_token` | Keycloak сообщает о сессиях, завершённых у него |

Права по режимам (с этапа 4а — составные роли в Keycloak, в токене — claim `permissions`): менеджер — `users.view`, `users.block`; админ — всё, включая
`users.roles.manage`, `users.sessions.manage`, `audit.view`.

### Правила

- **Менеджер работает только с покупателями** (как в боевом сервисе): сотрудников не видит в списке, их карточка,
  блокировка, доступ и сессии — 403 `users.staff_forbidden`.
- **С собой нельзя:** заблокировать (`users.self_restriction`), сменить роль (`users.self_role`), закрыть доступ
  (`users.self_access`).
- **Выдать admin** — только после недавнего входа (не старше 5 минут, claim `auth_time`), иначе 403
  `auth.reauthentication_required`: клиент отправляет на `/auth/login?reauth=true`, Keycloak спрашивает пароль и код 2FA.
- **Повторное действие без изменений** (уже заблокирован, та же роль, тот же доступ) — успех без изменений и без записи
  в журнал.
- **Роль изменилась или аккаунт заблокирован** — сессии пользователя завершаются (как в боевом сервисе), недоступный
  режим сбрасывается в customer.

## Как устроено

### Сервис ↔ Keycloak

Браузер к Admin API не ходит. Сервис проверяет права и вызывает Admin API от **служебной учётки клиента `sandbox-bff`**
(отдельный клиент не понадобился — учётка заложена ещё в этапе 1). Адрес Admin API — рядом с внутренним
`token_endpoint`, как и адрес выхода в этапе 3.

Права учётки — минимальные: `view-users`, `manage-users`, `view-events`, `query-clients` и **точечные права
(FGAP v2)** — `view` и `map-roles` только на клиенты приложений (`sandbox-api`, `sandbox-bff`, `account-console`).
`view-clients` целиком не выдан: он открывает секреты всех клиентов (проверено). `check-stand.sh` проверяет: учётка
видит только клиенты приложений, чужой клиент (`broker`) не находит, его секрет — 403, настройки realm не меняет.

| Возможность | В Keycloak |
|---|---|
| Режим | атрибут `active_mode` → после refresh токен уже с новым режимом |
| Блокировка | `enabled=false`, атрибуты `restriction_reason`, `restricted_at`, завершение сессий |
| Роль | роли клиента `sandbox-api` (выдача — через «доступные роли» пользователя) |
| Доступ к приложению | роль `access-denied` у клиента приложения + плагин (ниже) |
| Сессии | Admin API сессий; текущая — claim `sid` |
| Входы | события realm (`eventsEnabled`, хранятся 30 дней) |

### Доступ к приложению (плагин)

Встроенного «закрыть одно приложение» в Keycloak нет: завершить можно только сессию пользователя целиком (с SSO для
всех приложений), «отозвать согласие» работает лишь с согласиями и офлайн-токенами. Поэтому:

- **исполнитель политики клиентов** `sandbox-app-access` (профиль и политика `sandbox-app-access` в realm) — не выдаёт
  и не обновляет токены приложения пользователю с ролью `access-denied` этого клиента; работает для любого приложения,
  не только через наш сервис;
- **последний шаг входа** `sandbox-app-access-check` — страница «Доступ к этому приложению для вас закрыт» (в том числе
  при входе по живой SSO-сессии). Сценарий входа перестроен: способы входа — подсценарий `sandbox who`, затем
  обязательная проверка доступа (Keycloak не даёт смешать на одном уровне «один из способов» и «обязательный шаг»).

### Мгновенный отзыв

Проверка подписи и срока JWT идёт без Keycloak — поэтому раньше отозванный токен жил до конца срока. Теперь:

```
действие админа / выход / Keycloak back-channel ──► отметка в Redis ──► любой сервис: OnTokenValidated → 401
```

| Отметка (`auth:revoked:…`) | Когда | Какие токены отклоняются |
|---|---|---|
| `session:{sid}` | завершение сессии, свой выход, back-channel logout, а также все сессии пользователя при блокировке, смене роли, «выйти везде» | все токены сессии |
| `user:{sub}` = T | блокировка, смена роли, «выйти везде» | выданные строго раньше T (запасная — для токенов без sid) |
| `app:{azp}:{sub}` = T | закрыт доступ к приложению | токены этого приложения, выданные в эту секунду и раньше |

- Отметки живут 16 минут — дольше access-токена; потом старые токены истекают сами.
- **Проверка — в `Shared/Authentication`** (будущий NuGet): хук `OnTokenValidated`, работает, если сервис подключил
  хранилище. **Хранилище — `Shared/Authentication.Redis`**: `AddPlatformTokenRevocation(configuration)` — Redis
  (`ConnectionStrings:Redis`), проверка готовности (тег ready), кэш.
- **Кэш:** по стандарту платформы права доступа решает Redis напрямую с коротким L1 — HybridCache только в памяти
  (2 с, без второго уровня). Экземпляр, поставивший отметку, сразу сбрасывает свой кэш по тегам пользователя и сессии;
  на остальных отзыв доходит за время кэша.
- **Back-channel logout:** у клиента `sandbox-bff` в realm адрес `http://auth-service:8080/auth/backchannel-logout`;
  сервис проверяет `logout_token` (подпись ключами realm, издатель, адресат, событие, нет nonce) и ставит отметку на
  сессию. Так отзываются и сессии, завершённые в самом Keycloak (личный кабинет, его админка).

### Журнал

- **Действия сотрудников** — своя таблица `auth.audit_entries` (первая таблица сервиса). Поля — как у записи сервиса
  аудита боевой платформы: `action`, `object_type/id/name`, `changes` (jsonb, `{ "поле": { "old", "new" } }`),
  `actor_id/name/role`, `correlation_id`. Пишутся: `UserRestrictionChanged`, `UserRoleChanged` (как в боевом),
  `UserAppAccessChanged`, `UserLoggedOutEverywhere`. «По возможности»: журнал недоступен — действие выполнено, сбой — в лог.
- **Входы** — события Keycloak через Admin API (`LOGIN`, `LOGIN_ERROR` с причиной, `LOGOUT`); в карточке — `lastLoginAt`.
- **Миграции** — по стандарту платформы: `AuthDbContextFactory` для `dotnet ef`, одна таблица истории
  `auth.__ef_migrations_history`, `efbundle` в образе сервиса и контейнер `auth-migrator` в compose — сервис ждёт его
  успеха.

## Сравнение с боевым сервисом

| | Боевой | Песочница |
|---|---|---|
| Ответы | голые объекты, ProblemDetails без кодов | `Envelope`, коды ошибок |
| Список пользователей | без поиска и страниц | поиск, страницы, `hasMore` |
| Смена режима | новый только access-токен | новая пара (ротация refresh в Keycloak); режимы — по свежим ролям из Keycloak |
| Выдача admin | `actorPassword` | повторный вход (step-up): работает и с 2FA, кодом, ключом доступа |
| Своя роль | можно | нельзя (`users.self_role`) |
| Доступ к приложению, сессии других у админа, «выйти везде» | нет | есть |
| Отзыв access-токена | нет — живёт до 15 минут | сразу (Redis) |
| Журнал | внешний сервис аудита, 2 действия; входы — только в логах | своя таблица, 4 действия; входы — события Keycloak |
| `userAgent`, `deviceLabel` сессии, `loginCount` | есть | нет (Keycloak их не отдаёт; события хранятся 30 дней) |

## Грабли

- **`view-clients` открывает секреты всех клиентов**, а `query-clients` без точечных прав возвращает пустой список.
  Решение — FGAP v2: `view` и `map-roles` на нужные клиенты. Список клиентов фильтруется по правам; поиск — только
  `?clientId=…&search=true`, роль по имени не читается — id ролей берутся из «доступных ролей» пользователя.
- **FGAP ссылается на клиент по внутреннему UUID** — у клиентов приложений в realm JSON фиксированный `id`. UUID клиента
  уникален на весь Keycloak: в realm JSON нового проекта — свои UUID.
- **`GET /admin/realms/{realm}` Keycloak отдаёт любой админской роли** — проверять «не читает realm» бессмысленно,
  проверяется запрет на изменение.
- **PUT пользователя заменяет атрибуты целиком** — читать пользователя, менять нужное, писать обратно.
- **Отзыв по времени и секунды.** `iat` — в секундах: токен той же секунды, что и блокировка, не «раньше» отметки.
  Нашлось живым скриптом (не в каждом прогоне). Решение — отметки по sid всех сессий пользователя (их список берётся
  до завершения).
- **Свой кэш скрывал отзыв.** Запрос выхода сам кладёт в кэш «не отозван» — до 2 с этот же экземпляр принимал
  отозванный токен. Нашлось нестабильным тестом; решение — теги кэша и сброс при записи отметки.
- **Режим, роли, сессии в токене.** `auth_time` в токен кладёт маппер «user session note» — у нас свой scope
  `openid-min`, маппер добавлен. Порядок ролей в claim — как отдаёт Keycloak, сравнивать без порядка.
- **Мутанты, которые не собираются,** ничего не доказывают — строгие анализаторы ловят «всегда ложно» и т.п. Засчитаны
  только собранные.
- **Проверка, которая прошла бы и без отзыва:** «токен — 401» после неудачного refresh — cookie уже стёрты. Токен
  отправляется явно.

## Ограничения (для выводов)

- **Redis недоступен** — проверка отзыва пропускает токены (они живут ≤ 15 минут), предупреждение в лог.
- **Другие экземпляры** узнают об отзыве за время кэша (до 2 с).
- **Back-channel logout в Development** (`dotnet run`) не работает: Keycloak из контейнера зовёт `auth-service:8080`.
- **Список менеджера** — сотрудники убираются из страницы Keycloak, строк бывает меньше `pageSize`; роль каждой строки —
  отдельный запрос. Для прода — своя модель чтения.
- **Журнал «по возможности»** — без outbox запись может потеряться при сбое базы.
- **Админ приложения** (видит только своё приложение) — этап 4а/4б; сейчас доступ к приложению меняют менеджер и админ.
- Демо-эндпоинты `/demo/*` больше не нужны для проверки прав — их можно убрать вместе с матрицей `check-api.sh`.
