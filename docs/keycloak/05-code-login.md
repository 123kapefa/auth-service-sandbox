# Этап 5. Спайк: вход по коду — SMS и почта

**Статус:** ✅ готово · **Ветка:** `stage-5/code-login` · **Задача:** [#43](https://github.com/123kapefa/auth-service-sandbox/issues/43)

## Цель

Проверить, можно ли повторить в Keycloak вход по одноразовому коду боевого сервиса — и чего это стоит.
Встроенного входа по коду в Keycloak нет, поэтому это свой Java-плагин (SPI). Настоящих SMS в песочнице нет:
код «SMS» пишется в лог Keycloak, письма уходят в Mailpit.

| Что | Как |
|---|---|
| Форма входа | привычная: «Телефон или почта» + пароль, ниже «Войти по коду» и «Войти с ключом доступа» |
| Канал | по введённому: номер → SMS (в лог), почта → письмо (Mailpit) |
| Правила кода | как в боевом сервисе: 6 цифр, действует 300 с, повтор через 60 с, 5 неверных → блокировка 300 с |
| Лимиты | по номеру или почте, а не по попытке входа: новая попытка их не сбрасывает |
| Неизвестный номер или почта | тот же экран кода; покупатель создаётся **после** верного кода |
| 2FA | после кода — только у тех, кто её включил (как после пароля) |
| Номер телефона | приводится к логину **на сервере** для пароля и кода: `+7 (999) 000-00-01`, `8 999 000 00 01`, `9990000001` → `79990000001` |

## Как выглядит

1. Форма входа. Ввели номер или почту → «Войти по коду» (пароль не нужен).
2. Экран «Вход по коду»: «Отправили код в SMS на +79990000001» (или «письмом на …»), поле кода, «Отправить код ещё раз»
   (с подсказкой, через сколько секунд можно), «Войти по паролю».
3. Верный код → 2FA, если включена → обратно в приложение, как после пароля.

Письмо — простой текст: «Ваш код для входа: 311969. Код действует 5 мин…», тема «Код для входа».

## Как устроено

### Сценарий входа в realm

```
sandbox browser
├── cookie (уже вошёл)                          ALTERNATIVE
├── вход через внешнего провайдера              ALTERNATIVE
└── sandbox forms                               ALTERNATIVE
    ├── форма: телефон или почта + пароль       REQUIRED      sandbox-password-login   ← плагин
    ├── sandbox code login                      CONDITIONAL
    │   ├── условие: нажали «Войти по коду»     REQUIRED      sandbox-condition-code-requested  ← плагин
    │   └── код: отправка, экран, проверка      REQUIRED      sandbox-code-login       ← плагин
    └── sandbox conditional 2FA                 CONDITIONAL   (без изменений, этап 3а)
```

Форма входа одна на оба способа. «Вход» — проверка пароля, как у встроенной формы. «Войти по коду» — пароль не
проверяется, номер или почта запоминается в сессии входа (auth note — на сервере, браузер его не видит и не подменит),
и срабатывает условный подсценарий `sandbox code login`. После него — общий подсценарий 2FA, поэтому 2FA после кода
не потребовала ни строчки кода.

### Плагин

`infra/keycloak/providers/code-login` — Maven-проект, Java 21, Keycloak 26.4.7 (`provided`: в jar не попадает).

| Класс | Что делает | Зависит от Keycloak |
|---|---|---|
| `PhoneNormalizer` | номер → логин из цифр (правила боевого `PhoneCanonicalizer`) | нет |
| `CodeTarget` | куда слать: номер (SMS) или почта (письмо) | нет |
| `CodePolicy`, `CodeRules`, `CodeState` | правила кода: отправить или «рано», верно / неверно / блокировка; состояние ↔ строки хранилища | нет |
| `PasswordLoginForm` (+ `Factory`) | встроенная форма `UsernamePasswordForm` + нормализация номера + кнопка «Войти по коду» | да |
| `CodeRequestedCondition` (+ `Factory`) | условие подсценария: нажали «Войти по коду» | да |
| `CodeLoginAuthenticator` (+ `Factory`) | отправка, экран кода, проверка, поиск или создание пользователя, вход | да |
| `CodeStore` | состояние кода в `SingleUseObjectProvider` (ключ: realm + канал + номер/почта) | да |
| `SmsToLogSender`, `EmailCodeSender` | «SMS» в лог; письмо через SMTP realm, тексты — из сообщений темы | да |
| `CodeLoginNotes` | заметки сессии входа: куда слать код | да |

Логика, которую важно не сломать (правила кода, нормализация, выбор канала), — в классах **без Keycloak** и покрыта
юнит-тестами (47 тестов, JUnit 5). Классы с Keycloak проверяются скриптом на живом стенде.

### Тема

`infra/keycloak/themes/sandbox/login`:

- `login.ftl` — **копия** шаблона `keycloak.v2` с одной добавленной кнопкой «Войти по коду» (иначе кнопку не добавить);
- `sandbox-code-login.ftl` — экран кода, из макросов `keycloak.v2`;
- `messages/messages_{ru,en}.properties` — тексты экрана и письма (`sandboxCode*`).

### Сборка

`infra/keycloak/Dockerfile`: стадия Maven собирает плагин и **прогоняет юнит-тесты** (упавший тест — упавшая сборка
образа), затем плагин и тема кладутся в `quay.io/keycloak/keycloak:26.4.7`. Java и Maven на машине не нужны.
`compose.yaml` собирает этот образ (`auth_service-keycloak:26.4.7-sandbox`); тему на стенде поверх монтирует папкой,
чтобы править без пересборки.

### Новые пользователи

Неизвестный номер или почта получают **тот же** экран кода, что и существующие: по экрану не узнать, есть ли
пользователь. После верного кода создаётся покупатель:

| Вход по | Логин | Атрибуты | Роли |
|---|---|---|---|
| номеру | номер цифрами | `phone=+7…`, `active_mode=customer` | `customer` — из ролей по умолчанию realm |
| почте | почта | почта подтверждена (код из письма это доказывает), `active_mode=customer`, телефона нет | `customer` |

Keycloak пишет событие `REGISTER` с `register_method` = `sms-code` / `email-code`; вход — `auth_method` так же.
Заблокированный пользователь код получает, но после кода вход не пускает — «Учётная запись заблокирована».

## Тестовые пользователи

Логины `1234567890` и `0987654321` переименованы в `71234567890` и `70987654321`: по правилу боевого сервиса 10 цифр —
это номер с 7 впереди. В форме их по-прежнему можно вводить по-старому. Таблица — в [README](README.md).

## Как проверить

```bash
docker compose up -d --build --wait keycloak mailpit auth-service
```

```bash
scripts/keycloak/check-code-login.sh
```

Ожидается `Итого: 28 ✓, 0 ✗`: кнопка на форме; вход по коду из SMS (номер «как набрали»), неверный код, повтор раньше
60 с; новый покупатель по номеру; блокировка после 5 неверных (и её не обойти новой попыткой входа); вход по коду из
письма и новый пользователь по почте; 2FA после кода; отказы. Код скрипт берёт из лога Keycloak и из Mailpit.

Остальные проверки тоже проходят через новую форму: `check-stand.sh` 28, `check-api.sh` 48, `check-login.sh` 15,
`check-login-methods.sh` 21 (в нём — раздел про нормализацию номера на сервере).

Руками: http://localhost:8080 → «Войти» → номер → «Войти по коду» → код из лога:

```bash
docker compose logs keycloak | grep "SANDBOX SMS"
```

Письма — http://localhost:8025.

## Грабли

- **`UsernameForm` — `final`.** Шаг «кто вы» от встроенного класса не унаследовать. Пробовали вход в два экрана
  («кто вы» → способ) своим классом — отказались: лишний экран, «Забыли пароль?» только на втором, первый экран
  выдаёт, есть ли пользователь. `UsernamePasswordForm` наследовать можно — на нём и сделана форма.
- **Кнопку на форму без копии шаблона не добавить.** FreeMarker не умеет «расширить» шаблон — только заменить.
  Копия `login.ftl` помечена комментарием: при обновлении Keycloak сверить с новой версией.
- **Шаблон падает на отсутствующем атрибуте.** Экран ошибки «учётная запись заблокирована» сначала собирался без
  номера — FreeMarker падал, пользователь видел общую ошибку. Все экраны кода собираются одним методом.
- **Сначала отправка, потом сохранение.** Если сохранить код до отправки, а письмо не уйдёт, началась бы пауза
  60 с без письма.
- **Один TOTP дважды не принимается.** Два скрипта подряд с одним пользователем 2FA мешали друг другу; скрипты
  ждут свежее 30-секундное окно (`fresh_totp` в `lib.sh`).
- **`cut -c` на macOS режет байты, а не буквы** — кириллица в проверках обрезалась. Сравнение по началу строки —
  `starts` в `check-code-login.sh`.
- **Лимиты переживают прогоны скрипта.** Пауза 60 с от прошлого прогона — скрипт её дожидается (`code_start_fresh`).
- **Кэш ключей сервиса после пересоздания стенда** — как в этапе 3а: `docker compose restart auth-service`.

## Ограничения (для выводов)

- **«Внутренний» SPI.** При старте Keycloak предупреждает `KC-SERVICES0047`: аутентификаторы — внутренний SPI,
  совместимость между версиями не обещана. Каждое обновление Keycloak — пересборка плагина и прогон проверок.
- **Лимиты в памяти Keycloak** (`SingleUseObjectProvider`). Перезапуск стенда их сбрасывает; в кластере хранилище
  общее, но полный перезапуск кластера — тоже.
- **Лимиты только по номеру или почте.** Нет лимитов по IP и на «разные номера подряд»: бот может слать SMS на
  тысячи номеров (SMS-pumping). Встроенная защита Keycloak от перебора код не считает — пользователя на этом шаге
  ещё нет.
- **Любой номер получает SMS и становится покупателем после кода** — как в боевом сервисе, но это стоимость SMS и
  «мусорные» пользователи.
- **Письмо — простой текст.** Шаблоны писем Keycloak ждут пользователя, а неизвестной почте код уходит до его
  создания; HTML-письмо — свой `EmailTemplateProvider` или письмо собирать самим.
- **Форма сброса пароля** приводит номер к цифрам только скриптом темы — [#57](https://github.com/123kapefa/auth-service-sandbox/issues/57).
- **Тема показывает `+9990000002`** для 10 цифр без 7 (сервер понимает как `+79990000002`) — мелкая правка скрипта темы.

## Оценка до прод-качества

Грубо, в днях одного разработчика, который уже знает этот код. Без дизайна страниц входа ([#56](https://github.com/123kapefa/auth-service-sandbox/issues/56)).

| Что | Зачем | Оценка |
|---|---|---|
| Настоящий SMS-провайдер | клиент API, ретраи, таймауты, секреты из хранилища, код не в логах | 2–3 дня |
| Лимиты по IP и по «разным номерам» | защита от SMS-pumping и перебора; CAPTCHA при подозрении | 3–5 дней |
| Лимиты в распределённом хранилище | переживают перезапуск, общие для кластера (Infinispan / внешний) | 1–2 дня |
| HTML-письмо с кодом | свой `EmailTemplateProvider` или шаблон темы писем | 1–2 дня |
| Интеграционные тесты плагина | Testcontainers с Keycloak в CI вместо ручного стенда | 2–3 дня |
| Метрики и аудит | отправлено / неверно / заблокировано, стоимость SMS | 1–2 дня |
| Нормализация номера в сбросе пароля | [#57](https://github.com/123kapefa/auth-service-sandbox/issues/57) | 0,5 дня |
| **Итого** | | **~2–3 недели** |

И постоянно: на каждое обновление Keycloak — пересборка плагина, сверка копии `login.ftl`, прогон проверок
(~0,5–1 день на минорную версию, больше — на мажорную). Нужен человек, который готов поддерживать Java-код внутри
Keycloak, — для команды на .NET это отдельный навык.
