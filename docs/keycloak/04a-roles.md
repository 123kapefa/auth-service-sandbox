# Этап 4а. Динамические роли и права в Keycloak, умный рефреш

**Статус:** ✅ готово · **Ветка:** `stage-4a/roles` · **Задача:** [#58](https://github.com/123kapefa/auth-service-sandbox/issues/58)

## Цель

Роли и права меняются из админки, без изменения кода и без перелогина:

- **права** объявляет код сервиса, свои права можно добавлять из админки;
- **роли** — наборы прав, создаются и меняются из админки;
- у пользователя **сколько угодно ролей**, **роль = режим**;
- после изменения доступа — **умный рефреш** вместо выхода: клиент обновляет токен и показывает, что изменилось;
- **второе приложение** «Менеджер 1С» со своими правами и ролями и его **админ приложения**, который управляет
  только своим приложением.

## Модель в Keycloak

| Понятие | В Keycloak |
|---|---|
| Приложение | клиент с ролями (`sandbox-api`, `manager-1c`); носитель ролей и audience токена |
| Право | роль клиента с атрибутом `kind=permission`; `source=code` — объявлено кодом, `source=admin` — создано в админке |
| Роль (режим) | составная роль клиента `kind=role`, в составе — права; `builtin=true` — встроенная, не удалить |
| Роль по умолчанию | `customer` в `default-roles-sandbox`: есть у всех, снять нельзя |
| Активный режим | атрибут `active_mode` (приложение сервиса), `active_mode.{clientId}` (другие приложения) |
| Версии доступа | атрибут пользователя `access_version`, атрибут роли `version` (умный рефреш, ниже) |

**Маппер `sandbox-app-roles`** (плагин) кладёт в токен приложения:

- `role` и `available_roles` — только роли, без прав (стандартный маппер положил бы и права: роли составные);
- `permissions` — права активного режима: админ в режиме покупателя получает права покупателя;
- `access_version` и `mode_version` — версии доступа пользователя и роли активного режима.

У каждого приложения свой маппер в своей области токена: `sandbox-contract` (роли `sandbox-api`, режим
`active_mode`) и `manager-1c-contract` (роли `manager-1c`, режим `active_mode.manager-1c`). Сервисы читают права
из токена (`Shared/Authentication`), карты «роль → права» в коде нет.

**Каталог прав.** Системные права — константы в коде сервиса (`AuthServicePermissions`): при старте сервис заводит
недостающие в Keycloak (`source=code`), удалить их нельзя. Свои права (`source=admin`) — через API.

## API

Ответы — в `Envelope`, ошибки — с кодами. `{clientId}` — приложение: `sandbox-api` или `manager-1c`.

| Метод и путь | Право | Что делает |
|---|---|---|
| `GET /auth/admin/apps/{clientId}/permissions` | `roles.manage` | права приложения: системные и свои |
| `POST /auth/admin/apps/{clientId}/permissions { name, description }` | `roles.manage` | своё право |
| `DELETE /auth/admin/apps/{clientId}/permissions/{name}` | `roles.manage` | удалить своё право (системное — 409) |
| `GET /auth/admin/apps/{clientId}/roles` | `roles.manage` | роли с правами |
| `POST /auth/admin/apps/{clientId}/roles { name, description, permissions }` | `roles.manage` | своя роль |
| `PUT /auth/admin/apps/{clientId}/roles/{name} { description, permissions }` | `roles.manage` | описание и состав (ровно этот список) |
| `DELETE /auth/admin/apps/{clientId}/roles/{name}` | `roles.manage` | удалить свою роль (встроенную — 409) |
| `GET /auth/admin/apps/{clientId}/users?search&page&pageSize` | `users.roles.manage` | пользователи и их роли в приложении |
| `GET /auth/admin/apps/{clientId}/users/{id}/roles` | `users.roles.manage` | роли, роли по умолчанию, режимы, активный режим |
| `PUT /auth/admin/apps/{clientId}/users/{id}/roles { roles }` | `users.roles.manage` | выданные роли — ровно этот список |
| `PUT /auth/admin/users/{id}/role { role }` | `users.roles.manage` | как в боевом: одна роль приложения сервиса |
| `POST /auth/refresh` | refresh-cookie | новые токены; в ответе `changes` — что изменилось в доступе |

**Чьё право.** Админ проекта — право в токене (активный режим `admin`), действует на все приложения. Админ
приложения — то же право среди своих ролей **в самом приложении** (у роли `admin` «Менеджера 1С» есть `roles.manage`
и `users.roles.manage`). В приложение сервиса (`sandbox-api`) так не войти: там действуют только права режима из
токена, иначе админ в режиме покупателя обошёл бы режим. Нет права — 403 `apps.forbidden`.

### Правила

- **Имена:** право — с точкой (`orders.export`), роль — строчная латиница, цифры, дефис (`support`).
- **Встроенные роли** не удалить (`roles.builtin`); у `admin` нельзя убрать `roles.manage` (`roles.lockout`) — иначе
  управлять ролями станет некому.
- **Неизвестные права и роли** — 400 (`roles.unknown_permission`, `roles.unknown_role`); право вместо роли и
  `access-denied` ролью не считаются.
- **Свои роли** менять нельзя (`users.self_role`) — ни админу проекта, ни админу приложения.
- **Роль с управлением ролями** (в составе `users.roles.manage` или `roles.manage`) — выдать можно только после
  недавнего входа (5 минут), иначе 403 `auth.reauthentication_required`. Раньше так было только для `admin`.
- **Режим:** любая роль пользователя. Режим больше недоступен (или не выбран) — становится ролью по умолчанию,
  а без неё (в «Менеджере 1С» ролей для всех нет) — первой оставшейся ролью.
- **Админ приложения** не видит пользователей проекта, журнал, не блокирует аккаунт, не сбрасывает пароль и 2FA,
  не делает «выйти везде» — это уровень аккаунта, только админ проекта. Найти человека для выдачи роли — поиск
  `/auth/admin/apps/{clientId}/users` (логин, телефон, почта, роли в приложении).
- **Журнал:** `RoleCreated`, `RoleUpdated` (состав old/new), `RoleDeleted`, `PermissionCreated`, `PermissionDeleted`,
  `UserRoleChanged` (с приложением) — и от админа проекта, и от админа приложения.

## Умный рефреш

Смена роли больше не завершает сессии (в боевом сервисе и на этапе 4 — завершает). Старые токены сразу перестают
приниматься, но сессия жива: клиент обновляет токен и продолжает работу.

```
админ меняет роли / состав роли
  ├─► Keycloak: новая версия (атрибут access_version пользователя или version роли)
  └─► Redis: auth:changed:… = версия
запрос со старым токеном ──► 401, WWW-Authenticate: … error_description="access_changed", код auth.access_changed
клиент ──► POST /auth/refresh ──► новый токен (новые версии и права) + changes ──► плашка ──► повтор запроса
```

| Отметка (`auth:changed:…`) | Когда | Какие токены устарели |
|---|---|---|
| `user:{sub}` = версия | выданы или сняты роли (в любом приложении) | все токены пользователя с `access_version` меньше |
| `mode:{клиент}:{роль}` = версия | изменён состав роли, удалена роль, удалено право из её состава | токены в этом режиме с `mode_version` меньше |

- **Версии, а не время.** `iat` — в секундах: токен той же секунды, выданный до изменения, прошёл бы проверку по
  времени. Версия — миллисекунды изменения; её пишем в Keycloak (маппер кладёт её в токен) и в Redis. Порядок —
  сначала Keycloak, потом Redis: токен, выданный между ними, уже с новыми ролями, лишний рефреш ничего не ломает.
- **Понижение прав — сразу**, как и отзыв: проверка та же (`OnTokenValidated`, Redis + L1 2 с). Отозванный токен
  (блокировка, сессия) — обычный 401 без `access_changed`: обновлять бесполезно, нужно войти.
- **`changes` в ответе refresh:** `addedPermissions`, `removedPermissions`, `addedRoles`, `removedRoles`,
  `activeMode` — разница между прошлым access-токеном (из своей cookie) и новым; `null` — ничего не изменилось.
  Подпись при сравнении не проверяется: решения о доступе по нему не принимаются, это только показ.
- **Демо-страница** при 401 `access_changed` сама делает refresh, показывает плашку «Ваш доступ изменился: стало
  доступно / больше недоступно» и повторяет запрос.
- **Другие сервисы** получают то же из `Shared/Authentication`: проверка версий — в общем хуке, хранилище —
  `Shared/Authentication.Redis`; ключ режима — по своему audience (клиенту ролей).

## Второе приложение «Менеджер 1С»

| | |
|---|---|
| Клиент | `manager-1c` (bearer-only, носитель ролей и audience) |
| Права | `orders.view`, `orders.edit`, `reports.view`, `users.roles.manage`, `roles.manage` |
| Роли | `operator` (заказы), `accountant` (заказы на чтение, отчёты), `admin` (всё, включая управление ролями) |
| Режим | атрибут `active_mode.manager-1c` |
| Токен для отладки | клиент `manager-1c-cli` (ТОЛЬКО DEV, логин и пароль) |
| Пользователи | `79990000007` — админ 1С (в sandbox-api — покупатель), `79990000008` — оператор |

Служебной учётке выданы на `manager-1c` те же точечные права, что и на `sandbox-api` (FGAP v2: `view`, `map-roles`,
`manage`, `map-roles-composite`).

## Сравнение с боевым сервисом

| | Боевой | Песочница |
|---|---|---|
| Роли | три в коде (customer, manager, admin) | встроенные и свои, в Keycloak; у каждого приложения свои |
| Права | карта «роль → права» в коде сервиса | составные роли в Keycloak, права — в токене |
| Ролей у пользователя | одна | сколько угодно; роль = режим |
| Смена роли | выход из всех сессий | умный рефреш: 401 `access_changed`, refresh без перелогина, плашка |
| Изменение прав роли | новый релиз | из админки, действует сразу |
| Админ приложения | нет | управляет ролями и правами только своего приложения |

## Грабли

- **`map-roles-composite`.** Для изменения состава роли служебной учётке нужен этот scope FGAP v2 на клиент
  приложения — `manage` недостаточно.
- **Запятая в bash.** Внутри `"$(call … "{\"a\":1,\"b\":$X}")"` bash 3.2 (macOS) режет строку по запятой на два
  аргумента: уходили два кривых запроса, а проверка проходила случайно и оставляла роль `manager` без
  `users.block`. Тело — в переменной.
- **Отметка удалённой роли.** Роль удалили и создали заново с тем же именем — отметка удаления ещё в Redis, а у новой
  роли нет версии: токены её режима бесконечно получали `access_changed`. Новая роль сразу получает версию.
- **Прямая `customer` у демо-пользователей** — лишняя (она и так по умолчанию) и мешает отличить выданные роли от
  ролей по умолчанию. Из realm убрана.
- **Режим в другом приложении** — свой атрибут на приложение: один `active_mode` на все приложения смешал бы режимы.
  Профиль пользователя разрешает админу любые атрибуты (`unmanagedAttributePolicy: ADMIN_EDIT`).

## Ограничения (для выводов)

- **Каталог приложения** читается из Keycloak на каждый запрос админки (без кэша); список пользователей — роли
  каждой строки отдельным запросом.
- **Права админа приложения** — роли в приложении целиком, без режима: чтобы управлять «Менеджером 1С», не нужно
  переключаться в нём в режим `admin`.
- **Системные права «Менеджера 1С»** заведены в realm: сверку при старте делает только наш сервис для своего
  приложения; у настоящего второго сервиса — своя сверка через общий пакет.
- **Версии в Redis** живут 16 минут: старые токены к этому времени истекают сами.
- **Плашка** — на демо-странице; в своей админке — этап 4б.
