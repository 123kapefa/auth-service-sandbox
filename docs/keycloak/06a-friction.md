# Журнал трений встраивания

Что мешало, когда сервис входа встраивали как чужой проект. Каждое трение — что случилось, как обошли и что
предлагаем. Исправления — шаг 6а.6 (кроме отмеченных «исправлено»). Этап — [06a-embedding.md](06a-embedding.md).

## 6а.4 Новый проект: магазин «Заказы» + «Уведомления»

Проект «Демо-магазин» (realm `demo-shop`), сервисы — `samples/shop`, подключены пакетами `Platform.*` из фида, как
подключил бы их чужой проект. Проверка — `scripts/keycloak/check-shop.sh`.

| # | Трение | Как обошли | Предложение | Вес |
|---|---|---|---|---|
| 1 | **Новый покупатель приходил в «Заказы» без прав.** Права в токене — по режиму в приложении (`active_mode.orders`), а его ставит только смена ролей в админке. Покупатель, вошедший по коду, режима в «Заказах» не имел — `permissions: []`, все запросы 403 | — | **Исправлено:** режим не выбран — роль по умолчанию (маппер токена и проверка доступа по ключу) | блокер |
| 2 | **Токен по ключу адресован только сервису входа** (`aud=auth-api`). «Уведомлениям» пришлось принимать адресата сервиса входа; токен *человека* из сервиса входа проекта проходит подпись и адресата — отсекает его только `RequireService` | `Audience: auth-api` + `RequireService()` | **Исправлено (6а.6):** у ключа с правами в приложении в токене и его адресат (`aud` += код приложения); «Уведомления» — `Audience: notifications` | важно |
| 3 | **Права ключа есть только в сервисе входа** (`service.users.read`, `service.access.check`). Право «присылать уведомления» ключу «Заказов» не выдать — «Уведомления» держат свой список `client_id` в настройках | `Notifications:AllowedServices` | **Исправлено (6а.6):** права ключа в приложениях (`app:право`, админка «Права» → «В приложении …»); в токене — `app_permissions`, сервис видит свои; `RequireService(право)` | важно |
| 4 | **Права приложения кодом не объявить.** Сервис входа заводит свои права при старте, а «Заказы» — нет: права и роли заводит админ руками или скрипт (`setup.sh`). Опечатка в праве — молчаливый 403 | скрипт через API админки | **Исправлено:** `AddAppCatalog` в пакете — сервис при старте объявляет права и роли своим ключом (право `service.catalog.declare`); права из кода в админке не удалить, роли заводятся один раз | важно |
| 5 | **Режим в другом приложении человеку не переключить.** `POST /auth/mode` — только для приложения сервиса входа; страница «Заказов» в сервис входа и не попадёт (её токен — `aud=orders`). Сотрудник с ролями customer и manager работает как customer | атрибут `active_mode.orders` мастер-админкой Keycloak | **Исправлено (6а.6):** `POST /auth/mode { app, activeMode }`, `GET /auth/modes` и «Режим в приложениях» в кабинете | важно |
| 6 | **Перевыпуск ключа = остановка вызовов до перезапуска.** Старый секрет перестаёт действовать сразу, новый сервис берёт только из окружения при старте: между перевыпуском и перезапуском «Заказы» уведомлений не шлют | перезапуск с новым секретом | **Исправлено (6а.6):** плановый перевыпуск `keepTokens` (выданные токены доживают) и секрет из файла (`ClientSecretFile`) с перечитыванием | средне |
| 7 | **Пакет по умолчанию читает cookie `accessToken`.** Чужому сервису это неожиданно: на localhost браузер несёт cookie сервиса входа на любой порт | `AccessTokenCookie: ""` | **Исправлено (6а.6):** по умолчанию — только заголовок; сервис входа включает cookie явной настройкой | средне |
| 8 | **Вход в приложение — PKCE руками.** Cookie сервиса входа (BFF) «Заказам» не годятся (другой адресат, другой хост в бою); готового модуля входа для страницы нет — 60 строк на странице | своя страница (`Orders/wwwroot`) | **Исправлено (6а.6):** модуль входа `/sdk/platform-login.js` у сервиса входа проекта | средне |
| 9 | **Одна версия пакетов (0.1.0).** Перепакованный пакет с той же версией потребитель не видит — берёт старый из кэша NuGet | очистка `~/.nuget/packages/platform.*` | **Исправлено (6а.6):** `pack.sh` — `0.1.0-dev.<время>` и `platform-version.props`; `RELEASE=1` — чистая версия | средне |
| 10 | **Много адресов в настройках.** У каждого сервиса: Authority (внешний, для `iss`), MetadataAddress и TokenEndpoint (внутри сети), адрес сервиса входа — 4 адреса на одну систему | — | **Исправлено (6а.6):** `InternalAuthority` — один внутренний адрес; метаданные и адрес токена выводятся из него | мелочь |
| 11 | **Клиент API тянет наш стиль ошибок.** `Platform.AuthService.Client` возвращает `Result<T, Error>` (CSharpFunctionalExtensions, `Platform.SharedKernel`) — чужой проект получает их зависимостью | — | оставить (стандарт платформы) или исключения/свой результат в клиенте | мелочь |
| 12 | **Правила сборки песочницы цепляются к примерам.** `Directory.Build.props` и `Directory.Packages.props` из корня действуют на любой проект ниже по дереву | свои файлы в `samples/shop` | не нужно (в отдельном репозитории проекта не мешает) | мелочь |

Что прошло гладко: вход через страницы проекта (тема, название, вход по коду) для приложения с `--web`; проверка
токенов, прав и мгновенного отзыва в чужом сервисе — три строки в `Program.cs`; токен по ключу с повтором на 401;
чужие токены (другой проект, другой адресат, человек вместо сервиса) отклоняются без своего кода.

## 6а.5 Существующий проект: education-platform

Тестовая копия `archforge-testbed/education-platform` — LMS с OpenIddict + ASP.NET Core Identity.
Сервисы подключены пакетами `Platform.Authentication` напрямую (не через NuGet-фид), как подключил бы их
разработчик существующего проекта. Проверка — `scripts/keycloak/check-education-platform.sh`.

| # | Трение | Как обошли | Предложение | Вес |
|---|---|---|---|---|
| 13 | **Внутренние вызовы сервисов требуют роль `platform-service` в токене.** `RequireAnyRole(PlatformRoles.SERVICE, ...)` во всех `internal/`-endpoint'ах education-platform читает flat claim `role` из JWT. Наш токен ключа его не содержит: в нём `client_id`, но не `role: platform-service`. `oidc-hardcoded-role-mapper` Keycloak не подходит — он пишет в `realm_access.roles`, а не в flat `role` | маппер `oidc-hardcoded-claim-mapper` на каждый ключ-клиент (`apply.sh` шаг 3): `claim.name=role, claim.value=platform-service` → `RequireAnyRole` проходит | убрать зависимость от имени роли в чужом коде: `RequireService()` из `Platform.Authentication` или `RequireAnyRole` на claim `client_id` | важно |
| 14 | **NextAuth (Next.js) ожидал endpoint'ы OpenIddict, а не Keycloak.** Собственный AuthService возвращал OpenIddict-специфичный `/connect/userinfo` без `preferred_username`; NextAuth-конфигурация опиралась на internal URL `auth-service:8005` | переключить provider на `oidc` с двумя URL (issuer снаружи, wellKnown изнутри) и выбрать нужные claims вручную | включить в руководство «Как встроить»: Next.js + NextAuth — готовый фрагмент конфигурации | средне |
| 15 | **`docker-compose.keycloak.yml` нужен отдельный от `docker-compose.yml`.** Переменные среды каждого сервиса задаются в обоих файлах, и `extends:` Docker Compose не поддерживает нескольких merge-уровней для environment. Пришлось дублировать секцию `x-keycloak-auth` через YAML-якоря | YAML-якорь `&keycloak-auth` в override-файле | документировать паттерн в руководстве | мелочь |
| 16 | **`depends_on: !reset []` для фронтенда.** Оригинальный `docker-compose.yml` указывает `depends_on` на все сервисы; override не может убрать конкретные зависимости, только сбросить всё. Иначе compose отказывается поднять фронтенд без поднятого auth-service (OpenIddict) | `depends_on: !reset []` в override | документировать в `embedding-guide.md` | мелочь |

Что прошло гладко: замена `OpenIddict.Validation.*` на `Platform.Authentication` — одна строка в `Authentication.csproj`
и три строки в `AuthenticationExtensions.cs`; `UserScopedDataMiddleware` и `RolePermissions` без изменений (роли и права
в коде проекта, не в Keycloak); мгновенный отзыв — один пакет и одна строка; `AddJwtAuthentication` → новый сервис входа
прозрачно для 9 из 10 сервисов; вход через страницы Keycloak — PKCE в NextAuth без кастомного кода.
