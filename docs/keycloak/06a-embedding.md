# Этап 6а. Сервис входа как компонент

**Статус:** 🔄 идёт (6а.1–6а.4 и 6а.6 готовы, 6а.5 — впереди) · **Ветка:** `stage-6a/embedding` · **Задача:** [#98](https://github.com/123kapefa/auth-service-sandbox/issues/98)

## Цель

Сервис входа — готовый компонент: компания заменяет им свой вход или новый проект подключает его отдельным сервисом.
Сервисы проекта обращаются к нему и друг к другу с токенами, а посторонние — не могут: доступ только по нашему
согласию, **ключом на каждый сервис проекта** (как API-ключ).

## Ключи сервисов

Ключ — confidential-клиент Keycloak `service-{код}` только со служебной учёткой (без входа пользователей). Сервис
получает токен по `client_credentials` и ходит с ним в сервис входа и в другие сервисы проекта.

- **Выдача** — client registration API Keycloak по разрешению техника (initial access token,
  `Keycloak__RegistrationToken`, `scripts/keycloak/registration-token.sh`). Сервису входа право «управлять всеми
  клиентами» не нужно; управлять своим клиентом он может токеном управления из ответа регистрации (хранится в базе,
  зашифрован DataProtection). Не удалось выдать до конца — клиент удаляется.
- **Права** — роли клиента сервиса входа: `service.users.read` (читать пользователя), `service.access.check`
  (проверять доступ пользователя), `service.catalog.declare` (объявлять права и роли своего приложения — см.
  [ниже](#права-и-роли-приложения-из-кода)). В токене сервиса — только они, без ролей пользователя, плюс `client_id`.
- **Права в приложениях проекта** — роли клиента приложения у служебной учётки ключа (`notifications:notifications.send`;
  что можно выдать — `GET /auth/admin/services/grantable`). В токене — `app_permissions` по приложениям и адресат
  каждого из них в `aud`; сервис приложения видит в `permissions` только свои права (`TokenPermissionResolver`).
- **Перевыпуск** — новый секрет задаёт сервис входа. Срочный — старый секрет и его токены перестают приниматься сразу;
  плановый (`{"keepTokens": true}`) — выданные токены доживают срок. Сервис читает секрет из файла
  (`ServiceToken:ClientSecretFile`) при каждом новом токене — новый секрет без перезапуска.
- **Отзыв** — сначала гасятся выданные токены (мгновенный отзыв, как у пользователей), потом удаляется клиент.

API для сервисов (`RequireService`): `GET /auth/services/users/{id}`, `GET /auth/services/users?login=…`,
`GET /auth/services/users/{id}/access?permission=…`, `PUT /auth/services/catalog`. Админка: `/auth/admin/services` (выдать, список, перевыпустить,
права, отозвать) — только для пользователя с правом `services.manage`; сервис по ключу туда не попадает.

## Новый проект

Проект — отдельный realm из шаблона (клиенты `auth-api` и `auth-bff` — одинаковые во всех проектах):

```bash
scripts/project/create-project.sh shop "Магазин" https://auth.shop.example.com   # realm, секрет auth-bff
scripts/project/add-admin.py shop 79990000001 --email admin@shop.example.com      # первый админ
scripts/project/add-app.py shop orders "Заказы" --default-role customer --web https://shop.example.com
```

В бою — https обязателен (`sslRequired external`), почта — `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_USER` и
`SMTP_PASSWORD` (STARTTLS). `DEV=1` — локальный проект без https, почта в mailpit. Скрипты можно запускать повторно:
сделанные шаги пропускаются.

## Поставка

- **NuGet-пакеты** `Platform.*` (версия — `Directory.Build.props`): `scripts/package/pack.sh` → `artifacts/nuget`,
  подключение — `deploy/nuget.config.example`. Сервису проекта: `Platform.Authentication` (проверка токенов,
  `RequireUser`/`RequireService`, токен сервиса по ключу — секция `ServiceToken`), `Platform.Authentication.Redis`
  (мгновенный отзыв), `Platform.AuthService.Client` (`AddAuthServiceClient`: адрес — `AuthService:BaseUrl`).
- **Образы** `platform-auth-service`, `platform-auth-keycloak` и `platform-auth-realm-migrator` с той же версией: `scripts/package/build-images.sh`
  (`REGISTRY=… --push` — в реестр компании).
- **`deploy/compose.yaml`** — вставить в свой compose через `include:` со своим env-файлом по образцу
  `deploy/.env.example`. По умолчанию — боевой режим: Keycloak `start` за прокси с https (порты — на 127.0.0.1,
  `X-Forwarded-*` — только от прокси), сервис — Production, не root, ключи DataProtection зашифрованы сертификатом
  (`AUTH_DATA_PROTECTION_CERT_FILE`, без него не стартует). Без обязательных переменных compose не запускается и
  пишет, чего не хватает.

## Магазин: «Заказы» и «Уведомления»

Новый проект целиком, как его сделал бы чужой разработчик: проект «Демо-магазин» (realm `demo-shop`) и два мини-сервиса
в `samples/shop` — отдельное решение, пакеты `Platform.*` из фида (не ссылки на код песочницы).

| Сервис | Что делает | Доступ |
|---|---|---|
| «Заказы» (`Orders`, :5300) | страница магазина и API: мои заказы, заказать, все заказы и статусы | человек с токеном «Заказов» (`aud=orders`), права — из токена: `orders.view`, `orders.create`, `orders.manage` |
| «Уведомления» (`Notifications`, :5310) | шлёт покупателю письмо (есть почта) или «SMS» (в лог) | только сервис проекта по ключу с правом в приложении «Уведомления» (`notifications.send`, `notifications.read`) |

- **Вход** — страница «Заказов» ведёт на страницы входа проекта (Authorization Code + PKCE, клиент `orders-web` из
  `add-app.py --web`): телефон или почта, пароль или код; оформление — проекта и приложения (`platform_app=orders`).
- **Права** — объявлены в коде «Заказов» (`AddAppCatalog` в `Program.cs`): `customer` (по умолчанию у всех) —
  `orders.view`, `orders.create`; `manager` — `orders.view`, `orders.manage`. Руками в админке их не заводят.
- **Сервис сервису** — «Заказы» зовут «Уведомления» со своим ключом (`service-orders`: в сервисе входа — право
  объявлять свой каталог, в «Уведомлениях» — `notifications.send` и `notifications.read`);
  «Уведомления» своим ключом (`service-notifications`, право `service.users.read`) узнают у сервиса входа телефон и
  почту получателя. Ключ — секция `ServiceToken`, токен ставит `AddServiceToken()`.
- **Режим не выбран** — роль по умолчанию: новый покупатель приходит в приложение сразу с правами `customer` (маппер
  токена и проверка доступа по ключу; раньше прав не было — трение №1).

Поднять магазин (стенд песочницы поднят): `samples/shop/setup.sh` — проект и его сервис входа, приложение «Заказы»,
ключи, запуск сервисов (права и роли «Заказы» и «Уведомления» объявляют сами), сотрудник `79995550002` (режим «Сотрудник» — из кабинета) и покупатель `79995550003` (пароль `Test1234!`); секреты ключей — файлами в `samples/shop/.secrets` (секреты compose). Магазин — http://localhost:5300, письма — http://localhost:8025. Что мешало — [журнал трений](06a-friction.md).

## Права и роли приложения из кода

Права проверяет код (`RequirePermissions("orders.view")`) — значит, и объявлять их должен код: тогда право не забудут
завести, не опечатаются в имени и не удалят в админке, пока код его проверяет. Пакет `Platform.AuthService.Client`:

```csharp
builder.Services.AddAppCatalog(builder.Configuration, catalog => catalog
    .Permission(OrderPermissions.VIEW, "Свои заказы")
    .Role("customer", "Покупатель", OrderPermissions.VIEW));
```

При старте сервис отправляет каталог своим ключом (`PUT /auth/services/catalog`, право `service.catalog.declare`):

- **приложение** — по коду ключа: `service-orders` объявляет только `orders`; каталог сервиса входа — только он сам;
- **права** — главные в коде: создаются с `source=code` (в админке не удалить), описание обновляется; право,
  исчезнувшее из кода, не удаляется (может быть в ролях) — сервис пишет его в лог;
- **роли** — заводятся один раз встроенными; дальше их составом управляет админ, и следующий старт его правки не
  затрёт. Пустая роль по умолчанию из `add-app.py` получает состав из кода.

Как и зачем — в комментариях к коду: `AppCatalogBuilder` (что объявлять и что остаётся админу), `AppCatalogHandler`
(правила на стороне сервиса входа).

## Исправления 6а.6

По [журналу трений](06a-friction.md) — чтобы встраивать без обходов:

- права ключа в приложениях проекта и адресат токена (трения №2, 3) — «Уведомления» больше не держат список ключей;
- режим в любом приложении: `GET /auth/modes`, `POST /auth/mode { app, activeMode }`, карточка в кабинете (№5);
- плановый перевыпуск и секрет из файла (№6);
- пакет по умолчанию читает токен только из заголовка (№7);
- модуль входа для страницы приложения — `/sdk/platform-login.js` у сервиса входа проекта (№8);
- уникальная версия пакетов локального фида и `platform-version.props` (№9);
- один внутренний адрес Keycloak (`Authentication:InternalAuthority`) вместо трёх (№10).

## Проверка

```bash
scripts/keycloak/check-service-keys.sh   # ключи на стенде песочницы
scripts/keycloak/check-new-project.sh    # проект с нуля (demo-shop), свой экземпляр сервиса
scripts/package/build-images.sh && scripts/keycloak/check-deploy.sh   # поставка в боевом режиме
scripts/keycloak/check-shop.sh           # магазин: вход, права, сервис сервису по ключу, чужие запросы, перевыпуск
```

`check-shop.sh` (61 проверка) поднимает магазин с нуля (`setup.sh`) и проходит путь покупателя и сотрудника: новый
покупатель входит по коду и сразу получает права `customer`; заказ — уведомление по ключу (SMS или письмо в Mailpit);
покупателю чужие заказы и статусы — 403, сотруднику — можно; чужие токены (без токена, другого проекта, другого адресата,
человек вместо сервиса, ключ без права в «Уведомлениях») — 401/403; срочный перевыпуск ключа действует сразу, плановый — без остановки (новый секрет из файла, старые токены доживают), отозванный ключ — сразу; режим сотрудника — из кабинета; модуль входа `/sdk` отдаётся; права и роли «Заказов» — из их кода: право не
удалить в админке, ключу без права каталог не объявить, правка админа в роли переживает перезапуск сервиса.

`check-deploy.sh` ставит всё как чужой проект: свой compose с `include:`, прокси Caddy с https, проект без `DEV`;
входит админом, выдаёт ключ, перезапускает сервис и перевыпускает ключ (ключи DataProtection расшифрованы после
перезапуска) — и удаляет установку (`KEEP=1` — оставить).
