# Этап 4б. Своя админка доступа (UI)

**Статус:** ✅ готово · **Ветка:** `stage-4b/admin-ui` · **Задача:** [#59](https://github.com/123kapefa/auth-service-sandbox/issues/59)

## Цель

Своя админка вместо консоли Keycloak — только нужное: пользователи, роли и права, журнал. Консоль Keycloak остаётся
для техников (realm, клиенты, сценарии). Подключил сервис входа — получил админку на `/admin` (она в его образе);
приложение ставит на неё ссылку.

Два уровня админов (принцип наименьших прав):

| Действие | Админ проекта | Админ приложения |
|---|---|---|
| Видеть пользователей | всех в проекте (поиск, карточка) | с ролью в своём приложении + точный поиск по телефону или почте |
| Заблокировать аккаунт целиком | да | нет |
| Закрыть доступ к своему приложению | да (к любому) | да |
| Роли пользователей | во всех приложениях | только в своём |
| Роли и права приложения | во всех приложениях | только в своём |
| Сброс пароля и 2FA, «выйти везде» | да | нет |
| Журнал | весь проект (фильтр по приложению), входы | своё приложение |

Админ приложения — тот, у кого среди ролей **в самом приложении** есть права управления им (у роли `admin`
«Менеджера 1С»: `users.roles.manage`, `roles.manage`, `users.block`, `audit.view`). Админ проекта — права режима
`admin` в токене сервиса.

## Как устроено

### Админка (frontend/)

По стандарту платформы для SPA: Vite + React 19 + TypeScript (strict), Feature-Sliced Design (слои проверяет
ESLint), TanStack Query, axios, react-hook-form + Zod, Tailwind 4 и компоненты в стиле shadcn/ui, уведомления
`sonner`, Vitest + Testing Library. Подробно — `frontend/CLAUDE.md`.

| Адрес | Раздел | Кому |
|---|---|---|
| `/admin/` | обзор: права проекта и приложения под управлением | всем сотрудникам; покупателю — «нет доступа» |
| `/admin/users`, `/admin/users/{id}` | пользователи проекта: поиск, карточка (блокировка, роли по приложениям, доступ, сессии, пароль и 2FA) | `users.view`; блоки карточки — по своим правам |
| `/admin/journal` | журнал: действия (фильтры: действие, приложение, даты) и входы | `audit.view` |
| `/admin/apps/{clientId}/users` | пользователи приложения и их роли, доступ | `users.roles.manage` в приложении |
| `/admin/apps/{clientId}/roles` | роли с составом прав, свои права | `roles.manage` в приложении |
| `/admin/apps/{clientId}/journal` | журнал приложения | `audit.view` в приложении |

Меню и вкладки — по `GET /auth/admin/me`; это только удобство, доступ проверяет сервер.

**Вход и токены.** Токены — в httpOnly-cookie сервиса, страница их не видит; API — тот же origin. Клиент API:
ошибка из Envelope — с кодом; 401 с `access_changed` — умный рефреш (новые токены, плашка «Ваш доступ изменился»,
повтор запроса); истёк токен — refresh и повтор; refresh не принят — на вход с возвратом обратно. Действие требует
недавнего входа — в уведомлении кнопка «Войти заново» (`/auth/login?reauth=true`).

**Раздача.** Dockerfile собирает админку (`node:22-alpine`) и кладёт сборку в `wwwroot/admin`; адреса разделов
отдают её `index.html`. Для страниц `/admin` — CSP: скрипты и стили только свои, API — тот же origin, в рамку не
встроить. Исключение — тег `<style>`, который вставляет `sonner`: разрешён по хэшу (версия закреплена).

### API для админки (сервис)

| Метод и путь | Право | Что добавлено |
|---|---|---|
| `GET /auth/admin/me` | вошёл | права проекта и приложения под управлением (через проект или как админ приложения) |
| `GET /auth/admin/apps/{clientId}/users?search` | `users.roles.manage`* | без поиска — с ролью в приложении; поиск — точный телефон или почта |
| `GET /auth/admin/apps/{clientId}/users/{id}/roles` | `users.roles.manage`* | + `hasAccess`, `assignableRoles` (что можно выдать — без права читать каталог) |
| `PUT /auth/admin/users/{id}/apps/{clientId}/access` | `users.block`* | админ приложения — для своего приложения; в ответе только оно |
| `GET /auth/admin/audit?app=` | `audit.view` | фильтр по приложению; у записи — поле `app` (миграция `AuditEntryApp`) |
| `GET /auth/admin/apps/{clientId}/audit` | `audit.view`* | журнал одного приложения |
| `POST /auth/admin/users/{id}/password-reset` | `users.credentials.manage` | письмо Keycloak со ссылкой на смену пароля (24 часа) |
| `DELETE /auth/admin/users/{id}/two-factor` | `users.credentials.manage` | удалить OTP и коды восстановления — после недавнего входа |

\* право в токене (админ проекта) или среди ролей в самом приложении (админ приложения); в приложение сервиса
(`sandbox-api`) — только по токену.

**Закрыть доступ к «Менеджеру 1С».** Токены 1С выдаёт клиент входа (`manager-1c-cli`), а роли — на `manager-1c`:
атрибут клиента входа `sandbox.app` указывает плагину, у какого приложения смотреть `access-denied`. Плагин
запрещает и вход через страницу, и токен по паролю; мгновенный отзыв проверяет отметку и по клиенту входа (`azp`),
и по клиенту ролей (audience сервиса).

**Сброс пароля и 2FA** — уровень аккаунта, новое системное право `users.credentials.manage` (только у `admin`).
Свои — в «Настройках входа» (`users.self_credentials`). Нет почты — 409 `users.no_email`. В карточке — `hasTwoFactor`.

## Сравнение с боевым сервисом

| | Боевой | Песочница |
|---|---|---|
| Админка | своей нет (запросы к API вручную) | `/admin` в образе сервиса |
| Уровни админов | один | проект и приложение |
| Пользователи для админа приложения | — | только с ролью в приложении + точный поиск |
| Журнал | внешний сервис аудита | свой, с фильтром по приложению; входы — события Keycloak |
| Сброс пароля админом | задать пароль | письмо со ссылкой (пароль админ не видит) |
| Отключение 2FA админом | нет | есть, после недавнего входа |

## Грабли

- **Master-токен и VPN.** Запрос с хоста пришёл в Keycloak с адреса `172.66.x.x` (прокси на машине) — master-realm
  потребовал HTTPS, проверки с мастер-админкой упали. Скрипты берут токен изнутри контейнера Keycloak
  (`master-token.sh`).
- **CSP и `sonner`.** Уведомления вставляют `<style>` — строгая CSP его блокировала, а `'unsafe-inline'` не пропускает
  анализатор (S7039, и он прав). Решение — хэш содержимого и точная версия `sonner`; оформление дублирует собранный
  CSS. Стили, которые React ставит из JavaScript (CSSOM), CSP не трогает.
- **Вход по паролю мимо запрета.** Политика клиентов ловила только вход через страницу (`TOKEN_RESPONSE`): токен по
  паролю для закрытого 1С выдавался. Добавлено событие `RESOURCE_OWNER_PASSWORD_CREDENTIALS_RESPONSE`.
- **Названия встроенных клиентов** Keycloak — ключи перевода (`${client_account-console}`): вместо них — `clientId`.
- **Дата создания** у пользователей из импорта realm — 0 (1970): показывается «—».
- **Каталог ролей для админа приложения.** Выдавать роли (`users.roles.manage`) можно без права читать каталог
  (`roles.manage`) — список «что можно выдать» пришлось отдавать вместе с ролями пользователя.
- **Правки, которые тихо не применились.** Замена текста скриптом без проверки после форматирования Prettier: ссылка
  в обзоре и её тест остались старыми и совпадали друг с другом. Правки с заменой — только с проверкой, что текст
  найден.
- **Отказ при уходе на вход.** Отклонённый запрос успевал показать экран ошибки до перехода на страницу входа — теперь
  запрос не завершается, пока браузер уходит.

## Ограничения (для выводов)

- **Список пользователей приложения** собирается из держателей ролей (до 1000 на роль), страницы — в памяти.
- **Админ приложения** действует по всем своим ролям в приложении, без режима (не нужно переключаться в 1С в `admin`).
- **Закрыть доступ** админ приложения может только у приложения с ролью `access-denied`.
- **Входы** — события Keycloak (30 дней); у выхода нет логина — показывается id пользователя.
- **Нет E2E-тестов в браузере**: интерфейс — Vitest + Testing Library, путь пользователей — `check-admin-ui.sh` по API,
  проверка глазами — в браузере.
- **Husky и проверки перед коммитом** для frontend не подключены (в корне репозитория нет npm-проекта).
