## Цель

Свой личный кабинет пользователя вместо стандартного кабинета Keycloak и оформление под проект из админки.

## Кабинет

`/account/` сервиса входа — второе приложение фронтенда (`frontend/`, `npm run dev:account`), для любого вошедшего.
Постоянные ссылки для приложений проекта: `GET /auth/account` — кабинет (раньше вела в кабинет Keycloak),
`GET /auth/account/security` — раздел «Безопасность», `GET /auth/account/devices` — «Устройства».

- **Профиль** — `GET /me/profile`: телефон (логин; меняется через поддержку), почта и подтверждена ли она (пароль —
  в «Безопасности»). Данные — с
  сервера входа, не из токена: в токене почты нет, а после смены она устарела бы.
- **Сменить пароль, сменить почту** — ссылка `/auth/login?action=update-password|update-email&return_to=…`: сервис
  уходит на вход Keycloak с `kc_action` (Application Initiated Action). Keycloak показывает страницу действия в теме
  проекта; если вход был давно (больше 5 минут), сначала спросит пароль. Итог Keycloak передаёт в callback
  (`kc_action_status`), сервис — в адрес возврата (`action_status=success|cancelled|error`), кабинет показывает
  уведомление и убирает параметр. Неизвестное действие — `400 auth.action.unknown`; `action_status`, подложенный в
  сам return_to, сервис убирает — итог сообщает только Keycloak.
- **Безопасность** (`/account/security`, `GET /me/security`) — пароль (задан ли), приложения-аутентификаторы (2FA),
  коды восстановления (сколько осталось), ключи доступа: подпись и дата, без секретов. Подключить и удалить — тем же путём, действиями
  Keycloak: `configure-totp` (`CONFIGURE_TOTP`), `configure-recovery-codes` (`CONFIGURE_RECOVERY_AUTHN_CODES`, новые
  коды заменяют старые), `register-passkey` (`webauthn-register-passwordless`), `delete-credential&credential=<Id>`
  (`delete_credential:<Id>`, Keycloak спрашивает подтверждение). Id — только GUID, иначе
  `400 auth.action.credential_required`.

- **Устройства** (`/account/devices`) — где вы вошли: устройство («Chrome · macOS»), IP, когда была активность;
  «Выйти» на другом устройстве (`POST /security/sessions/{id}/terminate`), «Выйти на других»
  (`…/terminate-all-others`), «Выйти везде» — все другие и затем эта (`POST /auth/logout`), с подтверждением. Токены
  завершённой сессии отзываются сразу (отметка по sid). Ниже — **история входов** за 30 дней (`GET /security/logins`):
  удачные и неудачные с причиной («неверный пароль или код», «много попыток…»), IP, устройство; последние 50.

### Устройство сессии

Keycloak в Admin API не отдаёт браузер сессии — только IP. Поэтому сервис сам записывает его на возврате со страницы
входа (`/auth/callback`): `sid` и `sub` из только что полученного access-токена, User-Agent запроса — в таблицу
`auth.login_devices` (миграция `LoginDevices`). Второй вход в той же сессии (другое приложение по SSO) запись не
меняет. Подпись «браузер · система» строится из User-Agent при чтении (`DeviceLabels`), так что улучшенный разбор
подхватит и старые записи. Хранится 30 дней — как события входа (`eventsExpiration`); старые удаляются при записи.

- **По возможности.** База недоступна — вход всё равно проходит, сессии и история показываются без устройства.
- **«Неизвестное устройство»** — сессии, начатые мимо сервиса (кабинет Keycloak `account-console`) или до 6б.3, и
  браузеры, которые не узнали. У неудачной попытки входа сессии нет — устройство не известно.
- **История** — события Keycloak `LOGIN` и `LOGIN_ERROR` пользователя (фильтр `user` Admin API, право
  `view-events` у служебной учётки уже есть). Устройство входа — по `sessionId` события. Каким способом вошли
  (пароль, код, ключ) Keycloak в событии не пишет — колонки «Как» нет.
- В админке в сессиях пользователя теперь тоже видно устройство.

### Кто что проверяет

- **Свои ли учётные данные и можно ли их удалить** — проверяет Keycloak: действие ищет их у пользователя сессии. Чужой
  Id — без страницы подтверждения сразу возврат с `action_status=error`, данные другого пользователя на месте. Пароль
  удалить нельзя: ссылкой в обход кабинета Keycloak покажет подтверждение, но откажет («Credential type cannot be
  removed») — кабинет такой кнопки не показывает. Оба случая — в `check-account.sh`.
- **Коды восстановления — тоже второй шаг.** В realm подпоток 2FA включается, если есть приложение **или** коды
  (`conditional-user-configured`), а дальше на выбор — код из приложения или код восстановления. Удалил приложение,
  а коды остались — вход спрашивает код восстановления. Поэтому кабинет создаёт коды только при подключённом
  приложении, а если коды остались одни — предупреждает и предлагает удалить. Админка («выключить 2FA») удаляет оба
  типа сразу.
- **Недавний вход.** Если вход был давно (больше 5 минут) — Keycloak сначала спросит пароль. После подключения 2FA
  сессия, начатая без кода, для действий не годится: Keycloak спросит пароль **и код** (проверено в `check-account.sh`).
- **Кабинет Keycloak** (`account-console`) пока включён: в админке он считается приложением («личный кабинет остаётся
  открыт», когда пользователю закрыли доступ к приложению проекта). Закрывать ли его — решение отдельное.

### Почта меняется только после подтверждения

В realm проверка почты при входе выключена (`verifyEmail: false`). Без неё Keycloak сразу записал бы новую почту, и
тот, кто завладел сессией, сменил бы почту и сбросил через неё пароль. Поэтому у действия `UPDATE_EMAIL` включено
«Force Email Verification» (`config.verifyEmail`): Keycloak шлёт письмо на новую почту, а меняет её только после
перехода по ссылке — и сразу помечает подтверждённой. Остальных пользователей настройка не касается.

После отправки новой почты Keycloak показывает страницу «письмо отправлено» и в сервис не возвращает (итога в кабинете
нет). На ней — ссылка «Вернуться в приложение»: `baseUrl` клиента входа (`sandbox-bff`, в новых проектах `auth-bff`) —
`…/auth/account`. Без почтового сервера (`new-project.py` без `--smtp-host`) сменить почту нельзя: письмо не уйдёт.

### Realm

- `requiredActions` записан в `sandbox-realm.json` полностью (иначе импорт зарегистрировал бы только перечисленные):
  `UPDATE_EMAIL` включён, с `verifyEmail`. Новые проекты получают это из шаблона (`new-project.py`).
- Живой стенд и проекты, созданные до 6б, — миграция `0001-stage-6b` (ниже, «Проекты, созданные до 6б»).

## Оформление проекта

Админка, раздел «Оформление» (`/admin/branding`, право `branding.manage` — у роли `admin`): **название** проекта,
**логотип** (PNG, JPEG, WebP или SVG до 100 КБ), **акцент** (или серый без цвета; для тёмной темы — тот же или свой,
ниже) и **тема** страниц входа — как в
системе посетителя, всегда светлая или всегда тёмная. Справа — страница входа в миниатюре (при теме «как в системе» —
светлая и тёмная). Сохранили — следующая открытая страница входа уже в новом оформлении: тему пересобирать не нужно.

- **Где хранится — в Keycloak.** Название — `displayName` realm (его же видят письма и стандартные страницы Keycloak),
  логотип (data URL), акцент и тема — атрибуты realm `platform.branding.logo|color|color-dark|theme` (значение атрибута — `TEXT`,
  логотип до 100 КБ помещается).
- **Плагин `platform-branding`** (`BrandingResource`, в jar плагинов `code-login`) — `/realms/{realm}/platform-branding`:
  `GET` — всем, без входа (`Cache-Control: no-cache`; секретов в нём нет), `PUT` — только с токеном учётки, у которой
  роль realm **`manage-branding`**: она есть только у служебной учётки сервиса входа. Право `manage-realm` (менять
  весь realm: сценарии входа, почту, провайдеров) сервису для этого не выдаётся — `check-stand.sh` по-прежнему
  проверяет, что настройки realm он не меняет. Значения проверяет и плагин (цвет `#rrggbb`, тема, data URL картинки,
  размер), и сервис.
- **Сервис** — `GET/PUT /auth/admin/branding` (только человек с `branding.manage`), проверка значений (цвет
  сохраняется строчными), изменение — в журнал (`ProjectBrandingChanged`: что поменялось; логотип — только «был/стал»,
  без картинки). Ответы плагина: 401/403 — `branding.not_permitted` (нет роли), 404 — `branding.not_installed` (образ
  Keycloak без плагина).
- **Страница входа** (`login-theme/src/login/branding.ts`) — до первого показа читает оформление рядом со своим
  адресом (`…/realms/{realm}/platform-branding`, тот же origin — CORS не нужен), ждёт не дольше 1,5 с: не дождались —
  обычный серый стиль, вход важнее оформления. Тема — `data-theme` на `<html>` (светлые и тёмные токены — в
  `styles.css`), акцент — токены `accent` и `ring` (ниже), текст на акценте — тёмный или светлый по яркости цвета
  (WCAG). Логотип — рядом с названием над карточкой. Чужое в ответе (логотип не
  картинкой, цвет не `#rrggbb`) отбрасывается.
- **Без своего оформления** — как было: серый стиль, тема по системе, название realm.
- **Письма и кабинет** — 6б.5, ниже.

Проектам, созданным до 6б.4, и живому стенду — миграция `0001-stage-6b` (ниже, «Проекты, созданные до 6б»).

## Оформление приложения, письма и кабинет

Приложение может переопределить **название, логотип и акцент** проекта (тема — всегда общая). Админка: раздел приложения,
вкладка «Оформление» (только админ проекта, право `branding.manage`; приходит в права приложения из «кто я»): пустое
название, «как у проекта» у логотипа и акцента — берётся проектное; справа — страница входа в приложение в миниатюре.

- **Где хранится** — атрибуты клиента приложения (того, что с ролями: `manager-1c`, `orders`):
  `platform.branding.name|logo|color|color-dark`. Плагин: `GET …/platform-branding/apps/{clientId}` — своё (без значения — как у
  проекта), `PUT` — только учётке с `manage-branding`, нет клиента — `404 {"error":"app_not_found"}`. Сервис —
  `GET/PUT /auth/admin/apps/{clientId}/branding` (приложение — клиент с ролями, как в остальной админке; клиент только
  для входа — `404 apps.not_found`), в журнал — `AppBrandingChanged` с приложением, без картинки.
- **Итоговое** — `GET …/platform-branding?app={clientId}`: проект, поверх — заданное у приложения. Акцент
  приложения заменяет акцент проекта парой: свой цвет без своего тёмного — тот же цвет и в тёмной теме.
- **Какое приложение у страницы входа.** Тема передаёт плагину `client_id` и `tab_id` из kcContext (cookie сессии
  входа браузер отправляет сам). Плагин берёт приложение:
  1. из запроса входа — `platform_app`: его добавляет сервис, если вход начат с `/auth/login?app={clientId}` (вход
     через общий клиент сервиса `sandbox-bff`/`auth-bff`); Keycloak хранит его в сессии входа, так что и следующие
     страницы (код, 2FA, «забыли пароль») — в оформлении приложения;
  2. иначе по клиенту входа: `platform.app` (клиент `orders-web` из `add-app.py --web` → `orders`) или сам клиент.

  Без `app` и у клиента сервиса — оформление проекта. Неверный `app` (не похож на clientId) сервис отбрасывает,
  неизвестный — плагин не находит: оформление проекта.
- **Письма** (тема писем `platform`) — в сером квадратном стиле: логотип (или квадрат акцентом) и название над
  карточкой, кнопка — акцентом (письма всегда светлые — акцент светлой темы), линии — серые. Оформление шаблону даёт плагин: свой `EmailTemplateProvider`
  (`BrandingEmailTemplateProvider`, `order()` больше нуля — Keycloak берёт его вместо стандартного без настройки
  сервера) кладёт `branding` и подставляет название в `realmName`; письмо с кодом входа (`EmailCodeSender`) — так же.
  Письмо из входа (сброс пароля, подтверждение почты, код) — в оформлении приложения этого входа; из админки («ссылка
  на смену пароля») — проекта.
- **Логотип в письме — ссылкой**: `…/platform-branding/logo?app=…&v=…` (почтовые программы не показывают data URL;
  `v` меняется с картинкой — не покажут старую из кэша). Ответ — картинка с `Content-Security-Policy: sandbox` и
  `nosniff`: SVG, открытый по ссылке, ничего не выполнит. SVG-логотип в письмах не показывается (его не рисуют
  почтовые программы) — вместо него квадрат цветом; для писем лучше PNG.
- **Кабинет** — `GET /me/branding?app=…` (любой вошедший): название и логотип — в меню («Личный кабинет» — подписью),
  акцент — токены `accent`/`ring`, тема проекта — по умолчанию, пока пользователь не выбрал свою переключателем.
  Открыт из приложения — `GET /auth/account?app={clientId}` (и `…/security`, `…/devices`): кабинет запоминает
  приложение на вкладку и передаёт его дальше в ссылки действий (пароль, 2FA — страницы входа тоже в оформлении
  приложения). Не загрузилось — серый кабинет, как раньше.

### Акцент: только кнопки и активное, свой для тёмной темы

Один цвет на всё (кнопки, уголки карточек, линии таблиц, штриховка, плашки ошибок) путал: ошибку не отличить от
акцента, а тёмный цвет терялся в тёмной теме. Поэтому цвет проекта — **акцент**:

- красит только **основную кнопку, активный пункт меню (и квадрат у названия) и фокус** — токены `accent`,
  `accent-foreground`, `ring`; линии, рамки, уголки и штриховка — `primary`, всегда серые;
- **ошибки** (ошибка под полем, блок ошибки, неудачный вход в истории, сообщение Keycloak об ошибке) — токены `danger`
  (текст) и `danger-muted` (фон): всегда свой красный, бледной плашкой с тёмно-красным текстом (в тёмной теме —
  наоборот), не цвет проекта. Акцент — сплошная заливка, ошибка — плашка с «!»: их не спутать, даже если акцент красный;
- **для тёмной темы** — «как в светлой» или «другой цвет» (`colorDark`; задаётся только вместе с основным — иначе
  `400`, «Цвет для тёмной темы — только вместе с основным»). Кабинет и страницы входа ставят правила для обеих тем
  (таблица стилей через CSSOM — `adoptedStyleSheets`, CSP кабинета не пускает `<style>`: светлая, `data-theme="dark"` и
  системная тёмная) — переключили тему, акцент свой.

Ничего включать не нужно: плагин и шаблоны — в образе Keycloak (`docker compose up -d --build --wait`), роль
`manage-branding` — с 6б.4 (старым проектам — миграция `0001-stage-6b`).

## Проекты, созданные до 6б

Новые проекты получают всё из шаблона realm (`new-project.py`). Realm импортируется только в пустую базу Keycloak,
поэтому живой стенд песочницы и проекты, созданные раньше, после `git pull` сами ничего не получат: в админке нет
«Оформления», а почта меняется без письма. Для них — миграция настроек проектов `0001-stage-6b` (с этапа 11.6, бывший
`upgrade-6b.py`): мигратор применяет её сам при развёртывании, ко всем проектам на Keycloak, которым её ещё не
применяли ([migrations.md](../migrations.md#настройки-проектов-realm)):

```bash
docker compose up -d --build --wait            # образ Keycloak с плагином и темой 6б, сервис с кабинетом, мигратор realm
```

Что она делает в realm:

- **действия кабинета** — `UPDATE_PASSWORD`, `UPDATE_EMAIL`, `CONFIGURE_TOTP`, `CONFIGURE_RECOVERY_AUTHN_CODES`,
  `webauthn-register-passwordless`, `delete_credential`: включены (не зарегистрированы — регистрирует), у
  `UPDATE_EMAIL` — `verifyEmail` (почта меняется только после письма);
- **«Вернуться в приложение»** — `baseUrl` клиента входа (`auth-bff`; в песочнице `sandbox-bff`) = кабинет сервиса
  проекта: адрес сервиса берётся из redirect URI `…/auth/callback`;
- **оформление** — роль realm `manage-branding` у служебной учётки сервиса и право `branding.manage` в роли `admin`
  (то же, что `enable-branding.py`, — он остался для тех, кому нужно только оформление).

Админам проекта — войти в админку заново: право `branding.manage` придёт с новым токеном. Сервис перезапускать не
нужно: плагин проверяет роль учётки в базе Keycloak, а не в её токене. Начать с чистого листа (стенд, данные
удаляются) — `docker compose down -v`.

## Проверка

Весь этап — одной командой (стенд поднят: `docker compose up -d --build --wait`):

```bash
scripts/keycloak/check-6b.sh        # все проверки ниже по очереди и итог: по скрипту и общий
scripts/keycloak/check-6b.sh check-branding check-app-branding   # только часть
```

Ожидается `Итого: 140 ✓, 0 ✗` (`check-account.sh` 42, `check-devices.sh` 14, `check-branding.sh` 24,
`check-app-branding.sh` 26, `check-new-project.sh` 34). По отдельности:

```bash
scripts/keycloak/check-account.sh   # своим пользователем: смена пароля (и отмена), смена почты по ссылке из письма,
                                    # 2FA (код из приложения), повторный вход с кодом, коды восстановления, удаление
                                    # (и выключение 2FA целиком), чужие учётные данные — отказ
```

Ключ доступа зарегистрировать скриптом нельзя (нужно устройство): проверка доходит до страницы регистрации, сам ключ —
вручную в браузере (Touch ID).

Тесты: интеграционные — профиль, безопасность, действие при входе (и Id для удаления), итог в адресе возврата,
устройство сессии при входе (и вход без базы), сессии с устройством, история входов (только свои, LOGIN и
LOGIN_ERROR); юнит — `kc_action`, разбор учётных данных Admin API (счётчики кодов), события входа с сессией, подпись
устройства по User-Agent; фронтенд — профиль, безопасность, ссылки действий, уведомление и очистка адреса, устройства
(выйти на устройстве, «выйти везде» с подтверждением), история, давность («3 ч назад»).

Оформление (6б.4): интеграционные — прочитать и сохранить (только админ проекта), неверные значения, без изменений —
не сохраняется, отказ Keycloak; юнит — запросы к плагину и разбор его ответов (`KeycloakBrandingTests`), проверка
значений в плагине (`BrandingTest`, Java); админка — форма, логотип (тип и размер), миниатюры, меню; тема входа —
адрес плагина, тема и цвет на `<html>`, отброс чужого в ответе.

Оформление приложения (6б.5): интеграционные — прочитать и сохранить (только админ проекта, клиент без ролей — 404),
неверные значения, «как у проекта» — null, журнал приложения; вход с `app` (неверный отбрасывается), кабинет с `app`
(`/auth/account?app=`, `/me/branding`); юнит — запросы к плагину (`apps/{clientId}`, `?app=`, `app_not_found`), Java —
проверка своего у приложения, логотип из data URL, текст на цвете; админка — форма приложения, вкладка; кабинет —
приложение из адреса, тема проекта по умолчанию, ссылки действий с `app`; тема входа — `client_id` и `tab_id` в адресе
плагина.

Акцент для тёмной темы: интеграционные — сохранить `colorDark` (строчными, в журнал), неверный и без основного — отказ,
у приложения — парой; Java — проверка `colorDark`; админка — «Другой цвет» и миниатюра тёмной темы с ним; кабинет и
тема входа — правила акцента для обеих тем, линии и ошибки не трогают.

## Итоги этапа

- **Кабинет свой, чувствительное — у Keycloak.** Пароль, новая почта, секрет 2FA и ключ доступа вводятся только на
  страницах Keycloak (наша тема); сервис входа их не видит и не хранит. Кабинет только просит действие (`kc_action`)
  и показывает итог. Этого хватило на всё, что было в плане: профиль, пароль, почта, 2FA, коды, ключи, устройства.
- **Оформление без пересборки.** Название, логотип, акцент и тема — в Keycloak (realm и клиенты приложений), их
  читают страницы входа, письма и кабинет; плагин `platform-branding` пускает менять их только служебную учётку с
  узкой ролью `manage-branding`.
- **Чего Keycloak не даёт** — и как обошли: браузер сессии (пишем сами на callback), способ входа в событии (колонки
  «Как» нет), SVG в письмах (квадрат цветом), ключ доступа скриптом (только вручную).

Решить отдельно:

- **Кабинет Keycloak** (`account-console`) пока включён: им можно пользоваться в обход своего кабинета. Выключить —
  вместе с тем, как админка считает «личный кабинет остаётся открыт».
- **Письмо «почта изменена» на старый адрес** Keycloak не шлёт (в прогоне `check-account.sh` письмо ушло только на
  новый адрес): если сессией завладел чужой, владелец о смене почты не узнает. Нужно ли такое письмо — решить
  отдельно.
- Встраивание (6а.4–6а.6) проверит кабинет и оформление целиком: в новом проекте со своими сервисами и в копии
  существующего.
