# Этап 6б. Личный кабинет и оформление под проект

**Статус:** 🔄 идёт (6б.1–6б.3 готовы) · **Ветка:** `stage-6b/account-branding` · **Задача:** [#105](https://github.com/123kapefa/auth-service-sandbox/issues/105)

## Цель

Свой личный кабинет пользователя вместо стандартного кабинета Keycloak и оформление под проект из админки.
Чувствительные действия (пароль, почта, 2FA, ключ доступа) — на страницах Keycloak нашей темы по запросу из кабинета:
пароль и почта не проходят через код сервиса входа.

## Кабинет

`/account/` сервиса входа — второе приложение фронтенда (`frontend/`, `npm run dev:account`), для любого вошедшего.
Постоянные ссылки для приложений проекта: `GET /auth/account` — кабинет (раньше вела в кабинет Keycloak),
`GET /auth/account/security` — раздел «Безопасность», `GET /auth/account/devices` — «Устройства».

- **Профиль** — `GET /me/profile`: телефон (логин; меняется через поддержку), почта и подтверждена ли она (пароль —
  в «Безопасности»). Данные — с
  сервера входа, не из токена: в токене почты нет, а после смены она устарела бы.
- **Сменить пароль, сменить почту** — ссылка `/auth/login?action=update-password|update-email&return_to=…`: сервис
  уходит на вход Keycloak с `kc_action` (Application Initiated Action). Keycloak показывает страницу действия в теме
  проекта; если вход был давно (больше 5 минут), сначала спросит пароль. Итог Keycloak передаёт в callback
  (`kc_action_status`), сервис — в адрес возврата (`action_status=success|cancelled|error`), кабинет показывает
  уведомление и убирает параметр. Неизвестное действие — `400 auth.action.unknown`; `action_status`, подложенный в
  сам return_to, сервис убирает — итог сообщает только Keycloak.
- **Безопасность** (`/account/security`, `GET /me/security`) — пароль (задан ли), приложения-аутентификаторы (2FA),
  коды восстановления (сколько осталось), ключи доступа: подпись и дата, без секретов. Подключить и удалить — тем же путём, действиями
  Keycloak: `configure-totp` (`CONFIGURE_TOTP`), `configure-recovery-codes` (`CONFIGURE_RECOVERY_AUTHN_CODES`, новые
  коды заменяют старые), `register-passkey` (`webauthn-register-passwordless`), `delete-credential&credential=<Id>`
  (`delete_credential:<Id>`, Keycloak спрашивает подтверждение). Id — только GUID, иначе
  `400 auth.action.credential_required`.

- **Устройства** (`/account/devices`) — где вы вошли: устройство («Chrome · macOS»), IP, когда была активность;
  «Выйти» на другом устройстве (`POST /security/sessions/{id}/terminate`), «Выйти на других»
  (`…/terminate-all-others`), «Выйти везде» — все другие и затем эта (`POST /auth/logout`), с подтверждением. Токены
  завершённой сессии отзываются сразу (отметка по sid). Ниже — **история входов** за 30 дней (`GET /security/logins`):
  удачные и неудачные с причиной («неверный пароль или код», «много попыток…»), IP, устройство; последние 50.

### Устройство сессии

Keycloak в Admin API не отдаёт браузер сессии — только IP. Поэтому сервис сам записывает его на возврате со страницы
входа (`/auth/callback`): `sid` и `sub` из только что полученного access-токена, User-Agent запроса — в таблицу
`auth.login_devices` (миграция `LoginDevices`). Второй вход в той же сессии (другое приложение по SSO) запись не
меняет. Подпись «браузер · система» строится из User-Agent при чтении (`DeviceLabels`), так что улучшенный разбор
подхватит и старые записи. Хранится 30 дней — как события входа (`eventsExpiration`); старые удаляются при записи.

- **По возможности.** База недоступна — вход всё равно проходит, сессии и история показываются без устройства.
- **«Неизвестное устройство»** — сессии, начатые мимо сервиса (кабинет Keycloak `account-console`) или до 6б.3, и
  браузеры, которые не узнали. У неудачной попытки входа сессии нет — устройство не известно.
- **История** — события Keycloak `LOGIN` и `LOGIN_ERROR` пользователя (фильтр `user` Admin API, право
  `view-events` у служебной учётки уже есть). Устройство входа — по `sessionId` события. Каким способом вошли
  (пароль, код, ключ) Keycloak в событии не пишет — колонки «Как» нет.
- В админке в сессиях пользователя теперь тоже видно устройство.

### Кто что проверяет

- **Свои ли учётные данные и можно ли их удалить** — проверяет Keycloak: действие ищет их у пользователя сессии. Чужой
  Id — без страницы подтверждения сразу возврат с `action_status=error`, данные другого пользователя на месте. Пароль
  удалить нельзя: ссылкой в обход кабинета Keycloak покажет подтверждение, но откажет («Credential type cannot be
  removed») — кабинет такой кнопки не показывает. Оба случая — в `check-account.sh`.
- **Коды восстановления — тоже второй шаг.** В realm подпоток 2FA включается, если есть приложение **или** коды
  (`conditional-user-configured`), а дальше на выбор — код из приложения или код восстановления. Удалил приложение,
  а коды остались — вход спрашивает код восстановления. Поэтому кабинет создаёт коды только при подключённом
  приложении, а если коды остались одни — предупреждает и предлагает удалить. Админка («выключить 2FA») удаляет оба
  типа сразу.
- **Недавний вход.** Если вход был давно (больше 5 минут) — Keycloak сначала спросит пароль. После подключения 2FA
  сессия, начатая без кода, для действий не годится: Keycloak спросит пароль **и код** (проверено в `check-account.sh`).
- **Кабинет Keycloak** (`account-console`) пока включён: в админке он считается приложением («личный кабинет остаётся
  открыт», когда пользователю закрыли доступ к приложению проекта). Закрывать ли его — решение отдельное.

### Почта меняется только после подтверждения

В realm проверка почты при входе выключена (`verifyEmail: false`). Без неё Keycloak сразу записал бы новую почту, и
тот, кто завладел сессией, сменил бы почту и сбросил через неё пароль. Поэтому у действия `UPDATE_EMAIL` включено
«Force Email Verification» (`config.verifyEmail`): Keycloak шлёт письмо на новую почту, а меняет её только после
перехода по ссылке — и сразу помечает подтверждённой. Остальных пользователей настройка не касается.

После отправки новой почты Keycloak показывает страницу «письмо отправлено» и в сервис не возвращает (итога в кабинете
нет). На ней — ссылка «Вернуться в приложение»: `baseUrl` клиента входа (`sandbox-bff`, в новых проектах `auth-bff`) —
`…/auth/account`. Без почтового сервера (`new-project.py` без `--smtp-host`) сменить почту нельзя: письмо не уйдёт.

### Realm

- `requiredActions` записан в `sandbox-realm.json` полностью (иначе импорт зарегистрировал бы только перечисленные):
  `UPDATE_EMAIL` включён, с `verifyEmail`. Новые проекты получают это из шаблона (`new-project.py`).
- Живой стенд (realm импортируется только в пустую базу) — так же через Admin API. Проектам, созданным до 6б, — то же:
  `UPDATE_EMAIL` (включить, `verifyEmail`) и `baseUrl` клиента `auth-bff`.

## Проверка

```bash
scripts/keycloak/check-account.sh   # своим пользователем: смена пароля (и отмена), смена почты по ссылке из письма,
                                    # 2FA (код из приложения), повторный вход с кодом, коды восстановления, удаление
                                    # (и выключение 2FA целиком), чужие учётные данные — отказ
scripts/keycloak/check-devices.sh   # вход «с ноутбука» и «с телефона» (User-Agent), неудачная попытка; устройства
                                    # сессий, история входов с причиной, выйти на устройстве и на всех других
```

Ключ доступа зарегистрировать скриптом нельзя (нужно устройство): проверка доходит до страницы регистрации, сам ключ —
вручную в браузере (Touch ID).

Тесты: интеграционные — профиль, безопасность, действие при входе (и Id для удаления), итог в адресе возврата,
устройство сессии при входе (и вход без базы), сессии с устройством, история входов (только свои, LOGIN и
LOGIN_ERROR); юнит — `kc_action`, разбор учётных данных Admin API (счётчики кодов), события входа с сессией, подпись
устройства по User-Agent; фронтенд — профиль, безопасность, ссылки действий, уведомление и очистка адреса, устройства
(выйти на устройстве, «выйти везде» с подтверждением), история, давность («3 ч назад»).
