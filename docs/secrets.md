# Секреты: хранилище, проверка утечек, смена

Секреты сервиса входа живут в хранилище секретов **Infisical** ([ADR 0011](adr/0011-secrets-infisical.md)) и
подставляются в переменные окружения при запуске. В git, в `.env` и в файлах на машине их нет; в репозитории остаются
только заглушки разработки (`development-only`), их пропускает проверка утечек.

## Перечень

Имя — переменная в хранилище. Стенд песочницы (`compose.yaml`) и проект на `deploy/compose.yaml` называют часть секретов
по-разному: «стенд / проект». Владелец — кто заводит и меняет секрет.

| Секрет | Имя в хранилище (стенд / проект) | Кто читает | Владелец | Смена |
|---|---|---|---|---|
| Секрет клиента BFF (`sandbox-bff` / `auth-bff`) | `SANDBOX_BFF_CLIENT_SECRET` / `AUTH_BFF_CLIENT_SECRET` | сервис входа (`Keycloak__ClientSecret`), Keycloak (секрет клиента) | техник платформы | [скрипт, без потери сессий](#секрет-bff) |
| Разрешение на ключи сервисов (initial access token) | `KEYCLOAK_REGISTRATION_TOKEN` / `AUTH_REGISTRATION_TOKEN` | сервис входа (`Keycloak__RegistrationToken`) | техник платформы | [скрипт](#разрешение-на-ключи-сервисов) |
| Сертификат ключей DataProtection (PFX в base64) и его пароль | `AUTH_DATA_PROTECTION_CERT`, `AUTH_DATA_PROTECTION_CERT_PASSWORD` | сервис входа (`DataProtection__Certificate`) | техник платформы | [скрипт, с перекрытием](#сертификат-dataprotection) |
| Пароль базы сервиса входа | `POSTGRES_PASSWORD` / `AUTH_DB_PASSWORD` | Postgres, мигратор, сервис входа | техник платформы | [скрипт](#пароли-баз) |
| Пароль базы Keycloak | `KEYCLOAK_DB_PASSWORD` / `AUTH_KEYCLOAK_DB_PASSWORD` | Postgres Keycloak, Keycloak | техник платформы | [скрипт](#пароли-баз) |
| Пароль админа Keycloak (мастер-админка) | `KEYCLOAK_ADMIN_PASSWORD` / `AUTH_KEYCLOAK_ADMIN_PASSWORD` | Keycloak — только при первом запуске; скрипты техника | техник платформы | [вручную](#пароль-админа-keycloak) |
| Пароль почты (SMTP) | `SMTP_PASSWORD` | Keycloak (настройки почты проекта, хранит в своей базе) | админ проекта | [вручную](#почта-smtp) |
| Ключи Яндекс SmartCaptcha (серверный; клиентский — не секрет) | `SMARTCAPTCHA_SERVER_KEY` / `AUTH_SMARTCAPTCHA_SERVER_KEY` | Keycloak (плагин кодов) | техник платформы | [вручную](#ключи-внешних-систем) |
| Телефония и SMS (адрес шлюза с ключом) | `PHONE_PROVIDER_URL` | Keycloak (плагин кодов) | техник платформы | [вручную](#ключи-внешних-систем) |
| Яндекс ID (секрет приложения) | `YANDEX_CLIENT_SECRET` | Keycloak (вход через Яндекс ID) | админ проекта | [вручную](#ключи-внешних-систем) |
| Госуслуги (ЕСИА): ключ подписи ГОСТ | у сервиса подписи (`ESIA_SIGNER_URL`), в хранилище — только его адрес | сервис подписи | техник платформы | [вручную](#ключи-внешних-систем) |
| Секреты ключей сервисов проекта | у каждого сервиса свой (`ServiceToken__ClientSecret` или файл) | сервисы проекта | админ проекта (выдаёт в админке) | в админке, «Перевыпустить» ([06a](keycloak/06a-embedding.md)) |
| Секрет клиента переноса пользователей (этап 6, временный) | `LEGACY_IMPORT_CLIENT_SECRET` | Keycloak, `AuthService.LegacyImport` | техник платформы | удаляется вместе с клиентом после переноса |

Не секреты, хоть и рядом: `ESIA_CLIENT_ID`, `ESIA_CERTIFICATE_HASH`, `YANDEX_CLIENT_ID`, ключ сайта SmartCaptcha,
адреса и порты — им место в `.env` или `appsettings.*.json` ([окружения](environments.md)).

## Хранилище: Infisical

Проект `auth-service` в Infisical, окружения **dev** (стенд), **staging**, **prod** — у каждого свои значения и
свои права: учётка сервиса читает только своё окружение, людям прод доступен только по роли.

Как секреты попадают в сервис:

- **Docker Compose** (стенд, `deploy/compose.yaml`): `infisical run -- docker compose up` — CLI получает секреты
  окружения и запускает compose с ними в переменных окружения; compose подставляет их в `${…}` вместо `.env`.
  На диск они не пишутся. В песочнице это `scripts/secrets/run.sh <команда>`.
- **Kubernetes** (11.7): оператор Infisical (`InfisicalSecret`) кладёт секреты окружения в Secret, под берёт их
  переменными окружения; учётка оператора входит по Kubernetes Auth — без секрета на машине.

Вход в хранилище — учётка машины (Universal Auth: `INFISICAL_CLIENT_ID` и `INFISICAL_CLIENT_SECRET` меняются на токен
на час) или человек под своим входом (`infisical login`). Учётка машины — «нулевой» секрет: им открывается хранилище,
поэтому сам он в хранилище не лежит. На стенде — в `.secrets/infisical.env` (не в git, права 600), в бою — у платформы
(Kubernetes Auth, CI — секрет репозитория). Секреты пишет человек; учётка сервиса в бою только читает.

Сертификат DataProtection хранится как и остальные — строкой (PFX в base64): сервис читает его из
`DataProtection__Certificate`, файла нет. `DataProtection__CertificatePath` (файл PFX) остаётся для Kubernetes Secret,
смонтированного томом.

Что остаётся уязвимым: переменные окружения контейнера видит тот, у кого есть доступ к Docker на машине
(`docker inspect`); защита — доступ к машине, а не хранилище.

### Стенд песочницы с хранилищем

Нужны Docker и [Infisical CLI](https://infisical.com/docs/cli/overview).

```bash
scripts/secrets/infisical-local.sh up
```

Свой сервер Infisical в Docker (`infra/infisical/compose.yaml`, http://localhost:8280): админ стенда, проект
`auth-service` с окружениями dev, staging, prod и учётка стенда; всё для входа — в `.secrets/infisical.env`.

```bash
scripts/secrets/seed.sh --strip-env
```

Секреты стенда — в окружение dev: значения из `.env` (стенд уже поднят с ними: пароли баз и секрет BFF записаны в
томах), недостающие — новые случайные, сертификат DataProtection — новый. `--strip-env` убирает их из `.env`.
Чистый стенд (`docker compose down -v`) — `seed.sh --new`: все значения новые.

```bash
scripts/secrets/run.sh docker compose up -d --build --wait
```

Стенд с секретами из хранилища. Скрипты проверки — так же: `scripts/secrets/run.sh scripts/keycloak/check-login.sh`.
Без хранилища стенд по-прежнему поднимается с заглушками из `.env.example`.

Облачный Infisical или сервер компании — вместо `infisical-local.sh` задать `INFISICAL_API_URL`,
`INFISICAL_PROJECT_ID` и учётку машины (или `INFISICAL_TOKEN`) в окружении; остальное так же.

## Проверка утечек

**gitleaks** со стандартными правилами и исключениями из `.gitleaks.toml`:

- **CI** — `.github/workflows/secrets.yml`: вся история на каждый push и pull request; найденное значение в журнал не
  попадает (`--redact`).
- **Перед коммитом** — `.pre-commit-config.yaml`: `pip install pre-commit && pre-commit install`, дальше коммит с
  секретом не пройдёт. Вручную: `gitleaks git` (история), `gitleaks dir` (файлы, включая не добавленные в git).

Исключения — только то, что секретом не является, с пояснением: заглушки разработки (`development-only`,
`development-*-secret`, `sandbox-*`) и GUID в тестах. Настоящий секрет не исключают, а меняют.

### Если секрет утёк

1. Сменить его (раздел ниже) — удаление из истории git не помогает: копии уже у всех, кто клонировал.
2. Проверить журнал по нему: входы и выдачи токенов клиенту — события Keycloak, действия админов — журнал сервиса.
3. Ложное срабатывание — исключение в `.gitleaks.toml` с пояснением, отдельным коммитом.

## Смена секретов

Общий порядок: новый секрет — в хранилище, затем туда, где его проверяют, и перезапуск тех, кто его предъявляет.
Где проверяющий умеет помнить два значения (сервис входа — прежний секрет BFF и прежний сертификат), смена идёт
без отказов. Скрипты — для стенда; для проекта на `deploy/compose.yaml` в начале каждого скрипта написано, какие
переменные задать (имена секретов, `COMPOSE_FILE`, имя сервиса Keycloak).

### Секрет BFF

`scripts/secrets/rotate-bff-secret.sh`. Сессии от секрета не зависят: refresh-токены привязаны к клиенту, а не к
секрету. Отказать могут только обмен кода при входе и refresh в промежутке, когда сервис и Keycloak знают разные
секреты, поэтому:

1. В хранилище: секрет — новый, прежний — в `…_PREVIOUS`; сервис перезапускается и знает оба
   (`Keycloak__PreviousClientSecret`): Keycloak отверг новый (401 `unauthorized_client`) — запрос повторяется со
   старым.
2. В Keycloak секрет клиента меняется на новый (Admin API) — сервис сразу проходит с ним.
3. Прежний удаляется из хранилища, сервис перезапускается только с новым.

Ломается, если нарушить порядок: Keycloak с новым секретом раньше сервиса — входы и обновления токенов падают до
перезапуска сервиса (сессии не теряются, но страница отвечает ошибкой).

### Сертификат DataProtection

`scripts/secrets/rotate-data-protection-cert.sh`. Ключи DataProtection (ими зашифрованы cookie входа и токены
управления ключами сервисов) лежат в базе зашифрованными сертификатом. Меняется только сертификат, сами ключи — нет:

1. В хранилище: сертификат — новый, прежний — в `AUTH_DATA_PROTECTION_PREVIOUS_CERT` и `…_PASSWORD`. Сервис при
   старте расшифровывает ключи прежним и перешифровывает новым (в журнале — «re-encrypted»); новые ключи — сразу
   под новым.
2. Скрипт ждёт, пока в базе не останется ключей под прежним сертификатом.
3. Прежний удаляется из хранилища, сервис перезапускается только с новым.

Ломается, если поставить новый сертификат без прежнего: старые ключи не расшифровать — входы, начатые до смены,
не завершатся, токены управления ключами сервисов станут недействительными (ключи придётся перевыпустить). Сервис
пишет в журнал, какой ключ не расшифровался. Сертификат без срока годности не проверяется — смена по графику (раз в
год) или при утечке.

### Разрешение на ключи сервисов

`scripts/keycloak/registration-token.sh --store`: новое разрешение — в хранилище, сервис перезапускается, прежние
разрешения отзываются в Keycloak. Ключи, уже выданные сервисам, не затрагиваются; в промежутке до перезапуска выдать
ключ можно по старому.

### Пароли баз

`scripts/secrets/rotate-db-password.sh auth` (база сервиса) и `… keycloak` (база Keycloak): пароль роли меняется в
Postgres, затем в хранилище, затем перезапускаются мигратор и сервис (или Keycloak). Открытые соединения пула
работают, новые до перезапуска не откроются — перезапуск идёт сразу. Сессии Keycloak хранятся в его базе и
перезапуск переживают. Свои Postgres проекта (`AUTH_DB_CONNECTION`) — тот же порядок руками.

### Пароль админа Keycloak

Нужен Keycloak только при первом запуске (создать админа мастер-realm), дальше — скриптам техника. Сменить: в
мастер-админке (или `kcadm.sh set-password`), затем в хранилище. Ничего не ломается. Лучше — личные учётки техников в
мастер-realm и выключенный общий `admin`.

### Почта (SMTP)

Пароль хранится в настройках почты проекта в Keycloak; источник — хранилище. Сменить у почтового провайдера, затем в
Keycloak (Admin API: `PUT /admin/realms/{realm}` с `smtpServer.password`, или «Почта» в админке Keycloak), затем в
хранилище. Пока Keycloak со старым паролем — письма (коды, сброс пароля) не уходят, поэтому окно — минуты.

### Ключи внешних систем

- **SmartCaptcha**: новый серверный ключ в консоли Яндекс Облака, в хранилище, перезапуск Keycloak. Старый ключ
  удалить после перезапуска. На время перезапуска капча проходит (сбой капчи = пройдена, [ADR 0010](adr/0010-codes-call-before-sms.md)).
- **Телефония и SMS**: новый ключ у провайдера (если он позволяет два ключа сразу — без отказов), в хранилище,
  перезапуск Keycloak, затем отзыв старого.
- **Яндекс ID**: новый секрет приложения на oauth.yandex.ru, в хранилище, перезапуск Keycloak. Яндекс держит один
  секрет — между сменой и перезапуском вход через Яндекс ID отказывает.
- **Госуслуги**: ключ подписи ГОСТ — у сервиса подписи, меняется по регламенту ЕСИА (новый сертификат регистрируется
  в ЕСИА заранее, `ESIA_CERTIFICATE_HASH` — после).
