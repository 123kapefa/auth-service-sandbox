# 0005. Сервис сервису — по ключу: клиент Keycloak на каждый сервис

**Статус:** Предложено · **Дата:** 2026-10-05 · **Этап:** 6а

## Контекст

Сервисы проекта ходят к сервису входа и друг к другу. Чужой сервис пройти не должен; каждый сервис получает доступ
только с согласия админа и только к нужному.

## Решение

- **Ключ** — confidential-клиент Keycloak `service-{код}` только со служебной учёткой. Сервис берёт токен по
  `client_credentials` (`AddServiceToken`), секрет — из файла, перечитывается.
- **Права ключа** — роли клиента сервиса входа (`service.users.read`, `service.catalog.declare` …) и роли
  приложений проекта (`notifications:notifications.send`). В токене — адресаты этих приложений (`aud`) и
  `app_permissions`; приложение видит только свои права и проверяет `RequireService(право)`.
- **Выдача** — через client registration API Keycloak по разрешению техника: сервису входа не нужно право управлять
  всеми клиентами.
- **Перевыпуск** — срочный (старые токены сразу недействительны) и плановый (доживают срок); **отзыв** — сразу.

## Последствия

- Список «кому можно» не живёт в настройках каждого сервиса — его ведёт админ в одном месте.
- Токен человека не пройдёт туда, где ждут сервис, и наоборот; токен другого проекта или адресата — тоже.
- Ключей столько же, сколько сервисов: выдача и смена секретов — работа эксплуатации.

## Что отвергли

- **Один ключ на проект** — утечка открывает всё, права не разделить.
- **mTLS между сервисами** — нужна своя инфраструктура сертификатов, права всё равно описывать отдельно.
- **Списки `client_id` в настройках сервиса** — так было в 6а.4 (трение №3), убрано в 6а.6.
