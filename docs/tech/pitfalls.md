# Ловушки и неочевидное

То, что не видно из кода и стоило времени. Перед правкой Keycloak, realm, токенов или плагина — просмотреть нужный
раздел.

## Realm и Keycloak

- **Импорт realm — только в пустую БД** (`IGNORE_EXISTING`). Правка `sandbox-realm.json` старый стенд не меняет: для
  существующих проектов — нумерованная миграция realm ([migrations.md](../migrations.md#настройки-проектов-realm)).
  Как менять: сначала в консоли, затем перенести в JSON (*Realm settings → Partial export* показывает вид настройки).
- **После пересоздания стенда** очистить Redis (`redis-cli FLUSHALL`) и перезапустить сервис: отметки прошлого стенда
  сравниваются с версиями нового, и токены получают 401 `access_changed`; сервис держит ключи подписи старого realm до
  5 минут.
- **Профиль пользователя (Keycloak ≥ 24)**: без схемы молча отбрасываются незнакомые атрибуты (`phone`, `active_mode`).
  Нужны схема в `UserProfileProvider` и `unmanagedAttributePolicy: ADMIN_EDIT`; режим другого приложения — свой атрибут
  на приложение.
- **Свои client scopes отключают встроенные** (`profile`, `email`, `roles`, `basic`): `sub` добавляет scope
  `openid-min`, `auth_time` — маппер «user session note».
- **Default roles**: состав `default-roles-<realm>` задаётся в `roles.realm`, поле `defaultRole` только указывает на неё.
  Импорт пользователей роль по умолчанию не выдаёт — выдавать явно.
- **Плейсхолдеры `${ИМЯ}` в JSON** подставляются из окружения; нет переменной — текст остаётся как есть (поэтому
  `${username}` в схеме профиля не ломается).
- **Свои сценарии входа**: встроенные не править, копировать (`platform browser`). Если в JSON есть
  `authenticationFlows`, встроенные всё равно создаются.
- **Brute force**: 5 неверных паролей блокируют до 15 минут. Скрипты с заблокированным тестовым пользователем сбрасывают
  счётчик, иначе вместо «Account disabled» приходит «Invalid user credentials».
- **Мастер-токен — изнутри контейнера** (`kcadm.sh`, `scripts/keycloak/master-token.sh`): master-realm требует HTTPS для
  «внешних» адресов, а запрос с хоста при VPN или прокси приходит с публичного адреса.
- **Адреса Keycloak**: браузер и `iss` — внешний (`localhost:8180`), сервису изнутри — `keycloak:8180`. Нужен
  `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`. `end_session_endpoint` и `revocation_endpoint` приходят внешним адресом даже
  в контейнер — адрес выхода берётся рядом с `token_endpoint`. Иначе выход 500, cookie удалены, а сессия Keycloak жива.
- **Удалённый в админке внешний провайдер** Keycloak помнит в кэше привязок — после удаления перезапуск Keycloak.
- **Кабинет Keycloak (`account-console`) закрыт** (миграция 0004): клиенты `account` и `account-console` выключены, `/realms/<проект>/account/`
  отвечает 404, вход как `account-console` — 400. Они остаются в JSON realm явно и выключенными (иначе импорт падает на дубле).
  Выключенный клиент не считается приложением (`GetClientsAsync`, `GetAppAccessAsync`); выключенное приложение проекта админ в списках тоже не увидит.
  Письма админских действий (`execute-actions-email`, сброс пароля) идут без `client_id`: сессия по ссылке создаётся под служебным клиентом
  `_system`, а не под `account`, поэтому закрытие кабинета Keycloak их не ломает (`check-admin.sh` проходит ссылку до страницы смены пароля). Действия с учётной записью (пароль, почта, 2FA, ключи, телефон) идут
  через страницы входа по запросу кабинета (`kc_action` у клиента входа), а не через кабинет Keycloak.

## Права и Admin API

- **`view-clients` открывает секреты всех клиентов**, а `query-clients` без точечных прав возвращает пусто. Решение —
  FGAP v2 (`view`, `map-roles`) на нужные клиенты. Для изменения состава роли нужен `map-roles-composite`, `manage`
  недостаточно.
- **FGAP ссылается на клиент по внутреннему UUID**, он уникален на весь Keycloak: в realm нового проекта — свои UUID.
- **`GET /admin/realms/{realm}`** отдаётся любой админской роли; проверять нужно запрет на изменение.
- **PUT пользователя заменяет атрибуты целиком**: читать, менять, писать.
- **Роли выдаются через «доступные роли»** пользователя; роль по имени не читается. Роль, удалённая и созданная
  заново с тем же именем, должна сразу получить версию, иначе токены вечно получают `access_changed`.
- **Redis ACL**: файл `--aclfile` комментариев не допускает (запуск падает) — пример сделан конфигом с директивами `user`
  (`deploy/redis/redis.conf.example`). Пакет пишет отметки командой `SETEX`, а не `SET` — в ACL нужны `+setex` и `+psetex`; клиенту при
  подключении нужны `+client|setinfo`, `+client|setname`, `+client|id`, `+hello`, `+info`. `FLUSHALL` и `KEYS` клиент StackExchange.Redis без
  admin-режима не отправляет сам — отказ сервера (ACL) проверять подключением с `allowAdmin=true`.
- **Режим при сбое Redis — «закрыто»** даёт 503, а не 401: человек не разлогинен, сервис временно не может проверить токен.
- **Заглушки стенда в боевом Keycloak**: `Environment.isDevMode()` плагина — это `start-dev`; kind работает в `start`, поэтому ему нужен `ALLOW_STUBS`.
- **Демо-страница `/dev/`** лежит в образе (`wwwroot/dev`): образ один на стенд и бой, закрывает её `DemoPageConfiguration` (404, пока
  `DemoPage:Enabled` не включена; в Production включить нельзя). Новый способ раздачи статики должен сначала проходить это закрытие.
- **Выдавать роли (`users.roles.manage`) можно без права читать каталог (`roles.manage`)** — список «что можно выдать»
  отдаётся вместе с ролями пользователя. Но только роли в пределах собственных прав: без `roles.manage` не выдать и не
  снять роль, в которой есть чужие права (403 `users.role_above_own_rights`); в списке такие роли всё равно видны.
- **Названия клиентов** — ключи перевода (`${client_...}`): показывать `clientId`. Дата создания у импортированных пользователей — 1970.

## Токены, отзыв, кэш

- **`iat` в секундах**: токен той же секунды, что и блокировка, не «раньше» отметки. Отзыв сессий — по `sid` всех сессий
  пользователя (список берётся до завершения); смена доступа — версиями, не временем.
- **Собственный кэш скрывал отзыв**: запрос выхода сам клал в кэш «не отозван». Теги кэша и сброс при записи отметки.
- **Отметки Redis живут 16 минут**; если Redis недоступен, проверка пропускает токены (≤ 15 минут) и пишет в лог.
- **Порядок ролей в claim** — как отдаёт Keycloak, сравнивать без порядка.
- **Заголовок `X-Requested-With` (12.8)**: меняющий запрос с cookie токена без него — 403. Скрипты проверки ставят его через
  `$CSRF_HEADER` (`scripts/keycloak/lib.sh`); запрос с `Authorization` и без cookie — без заголовка. Забытый заголовок
  выглядит как «403 на refresh/logout, cookie не удаляются».
- **Имена cookie зависят от `Cookies:Secure`**: по https — `__Host-accessToken`/`__Host-refreshToken` (обе Path `/`), локально по http —
  `accessToken`/`refreshToken`. Скрипт, который читает cookie по имени из jar curl, должен знать, на каком адресе он идёт
  (check-deploy идёт по https: имена с приставкой). `curl` принимает `__Host-` только по https.
- **Токен сервиса по ключу и cookie**: на localhost браузер несёт cookie сервиса входа на любой порт — поэтому чтение
  cookie `accessToken` в пакете выключено по умолчанию.
- **Права ключа в приложении** — в `app_permissions` и в `aud`; сервис приложения видит в `permissions` только свои.
  Режим человека в приложении не выбран — берётся роль по умолчанию, иначе `permissions: []` и все запросы 403.

## Плагин Keycloak (Java)

- **Аутентификаторы — «внутренний» SPI** (`KC-SERVICES0047`): совместимость между версиями не обещана. Каждое
  обновление Keycloak — пересборка плагина, сверка копии `login.ftl` и прогон всех `check-*.sh`
  (~0,5–1 день на минорную версию).
- **`UsernameForm` — `final`**: наследовать нельзя. Вход в два экрана своим классом пробовали и отказались (лишний
  экран, «Забыли пароль?» только на втором). `UsernamePasswordForm` наследовать можно.
- **Кнопку на форму без копии шаблона не добавить**: FreeMarker умеет только заменить шаблон. Копия `login.ftl` помечена
  комментарием.
- **Шаблон падает на отсутствующем атрибуте** — все экраны кода собираются одним методом, чтобы атрибуты были всегда.
- **Сначала отправка, потом сохранение кода**: иначе при сбое письма началась бы пауза 60 с без письма.
- **`FreeMarkerProvider`** в Keycloak 26 — пакет `org.keycloak.theme.freemarker`.
- **Тема писем обязательна**: без `emailTheme: platform` код на почту не уйдёт («Не удалось отправить код»).
  Письма — HTML, но шаблоны Keycloak ждут пользователя, а неизвестной почте код уходит до его создания.
- **Счётчики лимитов не атомарны** и живут в памяти Keycloak (перезапуск сбрасывает; в кластере хранилище общее).
  Встроенная защита от перебора код не считает: пользователя на этом шаге ещё нет.
- **Эксплуатация**: пауза между кодами 60 с переживает прогоны скриптов; один TOTP дважды не принимается.
- **Политика клиентов `platform-app-access`** ловит и `TOKEN_RESPONSE`, и вход по паролю.
- **Страховка плагина** возвращает выключенными ключ доступа и коды восстановления, если их удалили на странице Keycloak
  в обход правил.

## Тема входа (Keycloakify)

- Страница — пустой `<div>` и `kcContext` в JavaScript (комментарии, висячие запятые, функции). Скрипты проверок читают
  его разборщиком `kc_context.py` (страница по `templateName`, адрес формы `url.loginAction`, ошибки `message.summary`).
- **Контролируемое поле с приведением к цифрам ломало ввод номера** — видимое поле без имени, на сервер уходит скрытое
  `username`. Хук показа пароля вынесен в компонент поля.
- **`localizationTexts` realm в браузер не передаются** — нужные дублируются в `i18n.ts`; в `withCustomTranslations`
  одинаковый набор ключей во всех языках. У части ключей нет русского перевода (2FA, коды восстановления, passkey) — свои.
  В стандартном ru-переводе 26.4 passkey назван «паролем»; 18 строк переопределены.
- **Без JavaScript не войти** (страницы рисует React). Jar темы ~2,3 МБ, сборка образа Keycloak требует Node. Обновление
  Keycloak может потребовать обновления Keycloakify.
- Письмо в SVG не работает — логотип квадратом цвета.

## Админка и кабинет (frontend)

- **Строгая CSP** (`'unsafe-inline'` не пропускает анализатор). `sonner` вставляет `<style>`: разрешён хэшем, версия
  закреплена, оформление дублирует собранный CSS. Стили из JavaScript (CSSOM) CSP не трогает.
- **Отклонённый запрос при уходе на вход** не должен завершаться, пока браузер уходит, иначе мелькает экран ошибки.
- **Правки заменой текста скриптом** — только с проверкой, что текст найден: после Prettier ссылка и её тест остались
  старыми и совпадали друг с другом.
- Нет E2E-тестов в браузере: интерфейс — Vitest, путь пользователя — скриптами по API. Husky для frontend не подключён.

## Кабинет и действия Keycloak (`kc_action`)

- **Устройство сессии Keycloak не отдаёт** (только IP): сервис пишет User-Agent сам на `/auth/callback` в
  `auth.login_devices` (30 дней, «по возможности»). В событии входа нет способа входа (колонки «Как» нет).
- **Почта меняется только после подтверждения**: в realm `verifyEmail: false`, поэтому у действия `UPDATE_EMAIL`
  включено `config.verifyEmail` — иначе владелец украденной сессии сменил бы почту и сбросил пароль. После отправки
  Keycloak в сервис не возвращает. Без почтового сервера сменить почту нельзя. Письмо на старый адрес не уходит.
- **Коды восстановления — тоже второй шаг**: подпоток 2FA включается, если есть приложение или коды. Удалил приложение,
  а коды остались — вход спрашивает код восстановления. Кабинет создаёт коды только при подключённом приложении;
  админка «выключить 2FA» удаляет оба типа.
- **Недавний вход** (больше 5 минут) — Keycloak сначала спросит пароль, после подключения 2FA — и код.
- **Пароль удалить нельзя** (Keycloak откажет); чужой Id учётных данных — возврат с `action_status=error`. Итог
  действия возвращается в адрес возврата как `action_status`; подложенный в `return_to` сервис убирает.

## Внешний вход (Яндекс ID, Госуслуги)

- **ЕСИА не обычный OAuth**: вместо секрета — подпись каждого запроса по ГОСТ Р 34.10-2012; подписывает отдельный
  сервис подписи (`EsiaSigner`: POST, тело — текст, ответ — PKCS#7 в base64), внутри Keycloak ГОСТ не подписать.
  `state` для ЕСИА — UUID, длинный `state` Keycloak хранится под ним на время входа (одноразово).
- Берём только подтверждённое: контакты ЕСИА с `vrfStu = VERIFIED`, у Яндекса — `default_phone`, `default_email`.
  Без телефона логин `yandex-<id>` / `esia-<oid>`.
- Привязка к существующему аккаунту — формой «только пароль» (`LinkPasswordForm`): встроенная форма даёт вписать
  чужой логин. Внешний вход не обходит ни 2FA, ни закрытый доступ к приложению.

## Перенос с BCrypt

- Обычное создание пользователя не сохраняет Id; сохраняет `partialImport` (нужен `manage-realm` — отсюда временный
  клиент `legacy-import`).
- **`OVERWRITE` удаляет существующего пользователя** (заменил тестового покупателя). В бою только `SKIP`.
- Пачка падает целиком, если Id занят под другим логином (409) — повторять по одному.
- Перехеш — в argon2 (по умолчанию Keycloak 26), не PBKDF2.
- Нужно окно без записи в старый сервис: повторный прогон не обновляет перенесённых. Сессии, refresh-токены, временные
  блокировки и счётчики не переносятся. Роли без пары (courier) переносятся покупателем с пометкой. Почты в старом
  сервисе нет — вход и сброс по телефону и коду.

## Сервис входа (.NET)

- **DI проверяется при старте в Development**: хендлеру нужен `IIdentityProvider`, без Keycloak сервис не стартует.
- **Ключи DataProtection** хранятся в базе, в боевом режиме шифруются сертификатом (без него сервис не стартует);
  в памяти они терялись бы вместе с незавершёнными входами.
- **`Dockerfile`**: на этапе restore копируются `.csproj` Shared-проектов, иначе `publish --no-restore` падает.
- **Back-channel logout в Development** (`dotnet run`) не работает: Keycloak из контейнера зовёт `auth-service:8080`.
- **Список менеджера** — сотрудники убираются из страницы Keycloak, строк бывает меньше `pageSize`.
- **Тест «чужого IP» в TestServer**: IP пустой — проверки по IP тестируются на middleware напрямую.
- **Анализаторы**: мутанты, которые не собираются, ничего не доказывают.
- **Bash 3.2 (macOS)** режет `"$(call … "{\"a\":1,\"b\":$X}")"` по запятой; `cut -c` режет байты, не буквы (кириллица).
  Тело запроса — в переменной, сравнение по началу строки — `starts`. Это не косметика: битое тело уходит в API как несколько запросов, сохранение
  молча не происходит, а проверки после него красные только на macOS (так были красными `check-branding` и `check-app-branding`,
  пока в CI на bash 5 они проходили, — #231).

### Логи и трассировка (13.2)

- **ASP.NET Core на уровне Information пишет адрес запроса со строкой запроса** (`Hosting.Diagnostics`: «Request starting … /auth/callback?code=…&state=…»)
  и адрес перехода (`Http.Result.RedirectResult`: «redirecting to …/auth?state=…»). Правила `Warning` для этих двух категорий — в каждом
  `appsettings*.json`; тест `Logs_NeverContainSecrets_OfLoginRefreshAndLogout` идёт в окружении Development, где общий уровень — Information.
- **.NET заменяет строку запроса в журнале HttpClient на `?*`** — а идентификатор в пути остаётся (`/admin/realms/x/users/{id}`); категория
  `System.Net.Http.HttpClient` в сервисе — Warning (ответы Keycloak считают метрики).
- **Свой журнал запроса** (`AuthService.Request`) пишет шаблон маршрута, а не путь: `/auth/admin/users/{userId}`. Область `RequestPath` ASP.NET Core
  добавляет сам (путь без строки запроса).
- **Идентификатор трассы в Keycloak** пишется, пока включена трассировка (`KC_TRACING_ENABLED`), даже при `always_off` (идентификатор
  берётся из `traceparent`); без `KC_LOG_CONSOLE_INCLUDE_TRACE` его в журнале нет. Допустимые значения `KC_EVENT_METRICS_USER_EVENTS`
  и `KC_EVENT_METRICS_USER_TAGS` Keycloak проверяет при старте (ошибки — части событий вроде `login_error` — отдельно не задаются).
- **Защита от CSRF и идентификатор трассы работают раньше журнала запросов** (стартовые фильтры): отказ 403 в журнал запросов не попадает —
  его пишет `CsrfHeaderMiddleware` (Warning).
- **Spans Keycloak несут сведения о людях** (`kc.details.username` — логин, `ipAddress`, `kc.userId`, id сессий, `client.address`, `url.query`): без
  коллектора с очисткой (`deploy/monitoring/otel-collector.yaml`) слать их в Jaeger или Tempo нельзя. Правки очистки — в этом файле; поле,
  которое Keycloak добавит в следующей версии, ловит раздел 5 `check-tracing.sh` только если оно похоже на значения проверки: после обновления
  Keycloak просмотрите spans в Jaeger глазами.
- **Необработанное исключение**: журнал запроса пишет статус 500 и Warning сам (иначе в `finally` был бы ещё 200); исключение пишет ASP.NET Core.
- **Идентификатор в теле ответа — `traceId` рядом с `isError`**, а не в `error`: добавляется только к ответам с ошибкой (`Envelope`) и к
  ответам, которые пишут защита (CSRF 403, 401, 503) вручную.
- **`check-code-limits.sh` читает журнал Keycloak** (`[CODE BUDGET] … исчерпан`): журнал Keycloak — строки JSON; кириллица в них без экранирования.

### Метрики (13.1)

- **Счётчик в Prometheus — только через `PrometheusMeterBridge`**: встроенный адаптер prometheus-net отдаёт счётчики .NET как
  `gauge` без `_total` (ADR 0016). Свой счётчик — `Counter<long>` в `AuthMetrics` или `PlatformAuthMetrics`.
- **Один набор меток на счётчик**: другой набор prometheus-net отклоняет, измерение пропадает (в логе — ошибка моста).
- **Метка не должна нести токен, номер, почту, идентификатор человека или сессии**; тест `Metrics_Labels_NeverCarryTokensOrCodes` и
  `check-metrics.sh` ловят очевидное.
- **Порт метрик сервиса в тестах — `0`** (`Metrics:Port`): десятки фабрик заняли бы один порт.
- **`MeterAdapter` по умолчанию публикует все Meter процесса** (QUIC, EF Core…) и дублировал бы мост — в сервисе включён фильтр;
  тест моста его выключает.
- **bash 3.2 режет `"$(… {10,} …)"` по запятой** — регулярные выражения в `check-metrics.sh` вынесены в переменные.
- **Grafana на стенде — порт 3030** (3000 часто занят dev-серверами): `GRAFANA_PORT`.

### Стадия 12: что легко сломать снова

- **`AUTH_ENVIRONMENT=Docker` открывает демо-страницу `/dev/`** (она включена в окружениях Development и Docker); значение — любая строка,
  технической защиты от «Docker в бою» нет. Боевое окружение — `Production` (`DemoPage:Enabled=true` в нём останавливает старт).
- **`limit_req` есть только в примере nginx** (`deploy/proxy`), у Caddy без плагина лимита нет; за общим адресом клиентов он
  общий — нужен `realip`.
- **Страница `/dev/` и любой другой интерфейс с cookie ставит `X-Requested-With`** на POST/PUT/DELETE (12.8); тест
  `Dev_EveryFetchSendsCsrfHeader` ловит забытый `fetch`.
- **`Cookies:Secure=false` вне локальной разработки** молча отключает `Secure` и приставку `__Host-` (сервис не падает: локальный
  запуск в Production по http допустим). В боевых настройках — `true`.
- **`AUTH_BIND=0.0.0.0` или `start-dev` в бою** публикуют весь Keycloak вместе с `/admin` и realm master: порт Keycloak отдают
  только прокси (`deploy/proxy`), проверка путей — `scripts/keycloak/check-public-paths.sh`.
- **`check-service-keys.sh`** падает с 401 на «ключ выдан», если токен регистрации клиентов выдан до пересоздания Keycloak или
  сервис запущен без него: `scripts/keycloak/registration-token.sh --write-env`, затем пересоздать сервис.
- **`check-budget-alerts.sh`** считает письма за сутки: второй прогон в тот же день не увидит письма о 80 % и 100 %
  (проверка рассчитана на свежие сутки; в CI — свежий стенд). Один раз не пришло письмо одному из админов — не повторилось.

## Встраивание чужого проекта

Что мешало при встраивании магазина «Заказы» + «Уведомления» (все пункты ниже исправлены, кроме 11–12):

1. Покупатель без выбранного режима приходил без прав → роль по умолчанию.
2. Токен по ключу был адресован только сервису входа → `aud` += код приложения.
3. Права ключа были только в сервисе входа → `app:право`, `app_permissions`, `RequireService(право)`.
4. Права приложения нельзя было объявить кодом → `AddAppCatalog`, `service.catalog.declare`.
5. Режим в другом приложении нельзя было переключить → `POST /auth/mode { app, activeMode }`, `GET /auth/modes`.
6. Перевыпуск ключа останавливал вызовы → `keepTokens`, секрет из файла.
7. Пакет читал cookie `accessToken` → по умолчанию только заголовок.
8. Вход страницы приложения — PKCE руками → модуль `/sdk/platform-login.js`.
9. Одна версия пакетов, кэш NuGet → `0.1.0-dev.<время>`, `platform-version.props`.
10. Много адресов в настройках → `InternalAuthority`.
11. Клиент API тянет стиль ошибок платформы (`Result<T, Error>`, `Platform.SharedKernel`) — принято как стандарт.
12. Правила сборки корня действуют на примеры ниже по дереву — в отдельном репозитории проекта не мешает.

### Существующий проект: education-platform

Тестовая копия LMS (OpenIddict, десять сервисов, Next.js), подключена пакетами `Platform.*`. Проверка —
`scripts/keycloak/check-education-platform.sh`. Что мешало:

13. **Внутренние endpoint'ы требуют роль `platform-service` в токене ключа** (`RequireAnyRole`, плоский claim `role`).
    `oidc-hardcoded-role-mapper` пишет в `realm_access.roles`, не подходит → `oidc-hardcoded-claim-mapper` на клиент
    ключа (`apply.sh`, шаг 3).
14. **NextAuth ждал endpoint'ы OpenIddict** (`/connect/userinfo`, внутренний адрес сервера) → provider `oidc` с двумя
    адресами (issuer снаружи, wellKnown изнутри), нужные claims вручную.
15. **Override Compose для среды каждого сервиса** — YAML-якорь `&keycloak-auth` (`extends:` environment не объединяет).
16. **`depends_on: !reset []` для фронтенда**: override не убирает отдельные зависимости, только сбрасывает все.
17. **Токен ключа не проходил проверку адресата (все внутренние вызовы — 401)**: сервисы принимают только `aud=education`, а у ключа
    без прав в приложении `aud=auth-api` → служебное право `education:internal.access`, выданное ключам. Скрипт по одним токенам
    этого не видел — нашлось только на настоящих сервисах.
18. **Пакет Redis занимал имя проверки здоровья `redis`** (у проекта такая уже есть; «Duplicate health checks») → имя
    `token-revocation-redis`.
19. **Сборка пакета называлась `Authentication`, как проект** (CS1704) → `AssemblyName` = `PackageId`.
20. **Скрипты падают на macOS (bash 3.2)** на `«$NAME»`: байт `»` попадает в имя переменной → `«${NAME}»`.
21. **Маппер роли привязан к клиенту Keycloak, не к ключу**: ключ, выданный заново, приходит без него и внутренние
    endpoint'ы молча отвечают 403 → повторный `apply.sh`; проверка смотрит `role` в токенах обоих ключей. Хотелось бы выдавать
    ключ с готовым маппером из сервиса входа.

Что прошло гладко: замена `OpenIddict.Validation.*` на пакеты — одна строка в `Authentication.csproj` и три строки
регистрации; мгновенный отзыв — один пакет; вход через страницы проекта — PKCE в NextAuth без своего кода.
