# 0019. Лимиты частоты запросов в сервисе: по IP и по ключу сервиса, скользящее окно

**Статус:** Предложено · **Дата:** 2026-11-23 · **Этап:** 13.4

## Контекст

Лимиты были только у кодов (Keycloak) и у `/realms/<код>` на прокси (ADR 0014). Начало входа, обновление токенов и API для сервисов не ограничены: один клиент мог
загрузить сервис, Keycloak и Redis, а подбор ключей сервиса или поток запросов «без токена» ничего не стоил.

## Решение

- **Встроенный лимитер ASP.NET Core** (`Microsoft.AspNetCore.RateLimiting`), один глобальный секционированный лимитер по пути запроса: `/auth/login`, `/auth/refresh`, `/auth/services/*`.
  Не атрибуты на эндпоинтах: новый адрес под `/auth/services/` попадает под лимит автоматически, и забыть его нельзя.
- **Ключ:** IP клиента (после `ForwardedHeaders`: за доверенным прокси — настоящий IP) для входа и refresh; `client_id` из проверенного токена для `/auth/services/*`; запросы к
  `/auth/services/*` без токена сервиса — по IP, строже. Лимитер стоит после аутентификации, до авторизации.
- **IPv6 — по сети /64**, IPv4-в-IPv6 приводится к IPv4: иначе один хост с /64 обходил бы лимит сменой адреса.
- **Скользящее окно** (6 сегментов), без очереди: нет двойного всплеска на стыке окон, отказ мгновенный. Ответ — `429`, `Retry-After`, обычная ошибка сервиса (`RATE_LIMIT`,
  `auth.rate_limited`, `traceId`).
- **Пороги — настройки** (`RateLimiting`), по умолчанию рассчитаны на сотни людей; 0 — без лимита группы, `Enabled=false` — без лимитов. Неверное значение останавливает старт.
- **Метрика** `auth_rate_limited_total{policy}` — без адресов и ключей в метках.
- **Проверка:** интеграционные тесты (429, `Retry-After`, разные IP и ключи, `X-Forwarded-For` от доверенного и недоверенного источника) и `check-rate-limits.sh` на стенде
  с низкими лимитами через временный override-файл compose.

## Последствия

- За NAT (офис, оператор) люди делят IP и лимит входа. Пороги по умолчанию это допускают (30 входов в минуту с адреса); при необходимости поднимаются.
- Если прокси не доверенный, лимит общий на всех: это ошибка настройки `ForwardedHeaders:TrustedNetworks`, описана в docs/environments.md.
- Лимиты живут в памяти каждой реплики: при N репликах эффективный предел до N раз выше. Общий счётчик (Redis) не нужен, пока цель — защитить сервис от перегрузки, а не точно
  считать запросы; перебор паролей и кодов ограничивают Keycloak и прокси.
- `Retry-After` берётся из лимитера и может быть больше фактического ожидания (до целого окна): клиент ждёт с запасом.
- Лимитер стоит после аутентификации (нужен `client_id` для `/auth/services/*`), так что разбор токена и проверка отзыва на каждый запрос остаются, в том числе на `/auth/login` и `/auth/refresh`. Осознанный компромисс: поток запросов с настоящим токеном до лимита доходит до Redis; вторая, ранняя проверка по IP удвоила бы счёт. Полный поток запросов отсекает прокси (пример — `limit_req` в nginx.conf.example).

## Что отвергли

- **Атрибуты `RequireRateLimiting` на эндпоинтах**: Core не должен знать о настройке, а новый адрес легко оставить без лимита.
- **Лимит в Redis**: добавляет зависимость и задержку на каждый запрос, а точность не нужна (см. выше).
- **Лимит только на прокси**: у сервиса нет ключа сервиса, прокси не отличит один ключ от другого, а развёртывание без прокси осталось бы без защиты.
