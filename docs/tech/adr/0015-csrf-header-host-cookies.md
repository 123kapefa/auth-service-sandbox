# 0015. Защита от CSRF заголовком и cookie с приставкой `__Host-`

**Статус:** Предложено · **Дата:** 2026-11-21 · **Этап:** 12.8

## Контекст

Cookie с токенами (`accessToken`, `refreshToken`) защищены `HttpOnly`, `Secure` и `SameSite=Lax`, без `Domain`. От CSRF
остаётся только `SameSite=Lax`. Если cookie когда-либо снова станут общими для поддоменов, страница на взломанном
поддомене сможет отправить POST без тела — перевыпуск ключа, сброс пароля, выход — и браузер приложит cookie. Второе
слабое место — подмена cookie с соседнего поддомена (cookie tossing): страница на нём ставит cookie с тем же именем и
`Domain=родитель`, и сервис не отличает её от своей.

## Решение

- **Собственный заголовок на меняющих запросах.** Запрос не из GET/HEAD/OPTIONS/TRACE, несущий cookie с токеном и не
  несущий `Authorization`, должен иметь заголовок `X-Requested-With` (любое непустое значение); иначе 403, код
  `auth.csrf_header_required`. Чужая страница такой заголовок поставить не может: браузеру понадобился бы CORS-предзапрос,
  а сервисы чужие источники не пускают. Проверка — middleware в пакете `Platform.Authentication`
  (`CsrfHeaderMiddleware`); оно подключается само вместе с `AddPlatformJwtAuthentication` (через `IStartupFilter`), поэтому
  каждый сервис проекта, читающий cookie с токеном, защищён без своих правок. Админка и кабинет ставят заголовок в единственном
  месте — клиенте API. Запросы с `Authorization` (сервис — сервису по ключу, приложения проекта по PKCE) и запросы без cookie
  с токеном (обратный вызов Keycloak) не затрагиваются: подделывать нечего.
- **Имена cookie по Secure.** По https (`Cookies:Secure=true`, боевой режим) — `__Host-accessToken` и `__Host-refreshToken`:
  браузер принимает их только с `Secure`, `Path=/` и без `Domain`, то есть подменить с соседнего поддомена нельзя. Локально
  по http (`Secure=false`: стенд, Development) `Secure` невозможна — имена прежние, `accessToken` и `refreshToken`. Одна
  настройка, а не две. Сервис входа читает access-cookie под тем же именем, под каким её ставит (`Authentication:AccessTokenCookie`
  задаётся им самим). Сервис проекта, читающий cookie, задаёт `Authentication:AccessTokenCookie=__Host-accessToken` и **не
  принимает** имя без приставки — иначе подменная `accessToken` с поддомена проходила бы.
- **`refreshToken` по https — `Path=/`.** `__Host-` требует `Path=/`, а у refresh-cookie было `Path=/auth/`. Мы выбрали
  защиту от подмены против сужения пути. Цена: refresh-токен (он живёт дольше access-токена) теперь уходит на любой путь хоста
  сервиса входа — статику, админку, кабинет, весь API — и на любой сервис, который стоит за тем же хостом. Поэтому на хосте
  сервиса входа недоверенных сервисов быть не должно, а прокси не пишет заголовок `Cookie` в журналы. Локально путь остаётся
  `/auth/`.
- **`auth_login` (состояние входа) — тоже `__Host-auth_login`, `Path=/`** по https: иначе страница на соседнем поддомене
  подбросила бы свою зашифрованную cookie, и жертва вошла бы в учётную запись атакующего (login CSRF).
- **Выход чистит и старые имена**: после перехода на приставку в браузере могли остаться `accessToken` и
  `refreshToken` — `Clear` снимает и их.

## Последствия

- Любой клиент с cookie-сессией на меняющих запросах обязан слать `X-Requested-With`: скрипты проверки
  (`scripts/keycloak/lib.sh`, `$CSRF_HEADER`), тесты, свои интерфейсы.
- Смена версии с cookie без приставки на с приставкой разлогинивает людей один раз: старые cookie сервис больше не читает.
- Защита держится на том, что сервисы проекта не включают широкий CORS (`AllowAnyHeader` вместе с `AllowCredentials`): иначе
  чужая страница сможет поставить заголовок. Своя проверка есть и у сервиса с нестандартным именем cookie
  (`Authentication:AccessTokenCookie`) — middleware сверяет и его.
- `Cookies:Secure=false` вне локальной разработки отключает и `Secure`, и приставку `__Host-`, и защиту от подмены; сервис
  на это не падает (локальный запуск в Production по http допустим), поэтому в боевых настройках `Cookies:Secure=true`
  проверяется при развёртывании.

## Что отвергли

- **Токен CSRF (двойная отправка или синхронизатор)** — нужен серверный или клиентский учёт токенов, а свой заголовок
  даёт то же свойство без состояния.
- **Проверка `Origin`/`Referer`** — заголовки бывают пустыми в части клиентов и прокси; заголовок надёжнее как дополнение к
  `SameSite`.
- **`__Secure-` вместо `__Host-` для refresh-cookie** — оставляет `Path=/auth/`, но не защищает от подмены с поддомена.
