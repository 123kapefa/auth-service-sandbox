# Архитектура

Как устроен сервис входа и почему части лежат там, где лежат. Решения с причинами — в [ADR](adr/README.md); здесь —
карта и сквозные механизмы. Как этим пользоваться — в [основной документации](../README.md).

## Из чего состоит

```
браузер ──► страницы входа (Keycloak + тема login-theme)
   │                     │
   │            Keycloak (realm = проект) ◄── плагин code-login (Java)
   │                     ▲   ▲
   ▼                     │   │ Admin API (служебная учётка, минимальные права)
сервис входа (.NET, BFF) ┘   │
 админка /admin, кабинет /account, API  ──► Redis (отметки отзыва и версий доступа)
   │                                    ──► Postgres сервиса (журнал действий)
   ▼
сервисы проекта (пакеты Platform.*): проверяют токен сами, ходят друг к другу по ключам
```

| Часть | Где | Зачем |
|---|---|---|
| Keycloak 26.4 и его БД | `compose.yaml`, `infra/keycloak/` | пользователи, пароли, сессии, токены, 2FA, ключи доступа; realm — один проект |
| Realm как код | `infra/keycloak/realm/sandbox-realm.json`, шаблон нового проекта | воспроизводимые настройки; импорт только в пустую БД, старым стендам — мигратор |
| Плагин Keycloak (Java) | `infra/keycloak/providers/code-login` | вход по коду, форма входа с нормализацией номера, BCrypt, доступ к приложению, маппер ролей, оформление, внешние провайдеры (Яндекс ID, Госуслуги), лимиты и бюджет кодов, способы входа, смена номера |
| Тема входа и писем | `login-theme/` (Keycloakify, React + FreeMarker) | страницы входа и письма в стиле проекта; собирается в jar внутри образа Keycloak |
| Сервис входа | `src/AuthService.*` (.NET) | BFF (вход, cookie, refresh, выход), режимы, API админки и кабинета, ключи сервисов, журнал |
| Админка и кабинет | `frontend/` (React, FSD) | свой интерфейс вместо консоли Keycloak; попадает в образ сервиса |
| Общие библиотеки | `src/Shared/Authentication*`, пакеты `Platform.*` | проверка токена, политики, права, отзыв, токен сервиса по ключу — подключает каждый сервис проекта |
| Мигратор настроек | `scripts/project/migrate-realms.py`, образ `realm-migrator` | нумерованные миграции realm, версия — атрибут realm |
| Перенос пользователей | `src/AuthService.LegacyImport` | разовый перенос с BCrypt-хэшами; после переезда не нужен |
| Заглушка внешних провайдеров | `infra/idp-stub/` | вход через Яндекс ID, Госуслуги, телефонию и капчу на стенде без ключей |
| Развёртывание | `deploy/`, `deploy/helm/platform-auth`, `.github/workflows/` | Compose, Helm, CI, релиз по тегу |

Правило границы: **пароли, секреты 2FA и ключи доступа видит только Keycloak.** Сервис входа их не получает — кабинет
просит у Keycloak действие (`kc_action`) и показывает итог ([ADR 0008](adr/0008-own-ui-sensitive-in-keycloak.md)).

## Модель: проект, приложение, роль

- Проект = realm Keycloak. Люди и страницы входа свои, проекты друг друга не видят
  ([ADR 0002](adr/0002-project-realm-app-client.md)).
- Приложение = клиент Keycloak, носитель ролей и адресат токена (`aud`). Аккаунт один на проект, права в каждом
  приложении свои.
- Право = роль клиента с атрибутом `kind=permission` (`source=code` — объявлено кодом, `source=admin` — создано в
  админке). Роль = составная роль клиента `kind=role`, в составе права; `builtin=true` — не удалить.
- Роль = режим. У человека сколько угодно ролей, работает он в одной: атрибут `active_mode` (приложение сервиса) или
  `active_mode.{clientId}` (другие приложения). Режим больше недоступен — становится ролью по умолчанию.
- Права и роли — в Keycloak, объявляет их код приложения ([ADR 0003](adr/0003-permissions-in-keycloak.md)).

## Токен

Access-токен — 15 минут, подпись RS256, проверка по ключам realm без обращения к Keycloak.

| Claim | Что |
|---|---|
| `iss`, `aud` | realm; приложение-адресат (у ключа с правами — ещё и адресаты приложений) |
| `sub`, `sid` | пользователь; сессия |
| `role`, `available_roles` | роли приложения (без прав) |
| `active_mode`, `permissions` | активный режим и права этого режима |
| `access_version`, `mode_version` | версии доступа пользователя и роли режима (умный рефреш) |
| `phone`, `auth_time` | телефон; время входа (для «недавнего входа») |
| `app_permissions` | у токена сервиса по ключу: права в приложениях |

Маппер `platform-app-roles` (плагин) кладёт `role`, `available_roles`, `permissions` и версии. Стандартный маппер
добавил бы и права, потому что роли составные. Свои client scopes realm отключают встроенные, поэтому `sub` даёт
scope `openid-min`.

## Вход в приложение (BFF)

1. `GET /auth/login?return_to=` — сервис кладёт state, PKCE-verifier и `return_to` в зашифрованную одноразовую cookie
   `auth_login` (10 минут) и отправляет на Keycloak (Code + PKCE S256).
2. `GET /auth/callback` — обмен кода на токены, cookie `accessToken` (Path `/`, живёт как токен) и `refreshToken`
   (Path `/auth/`), переход на проверенный `return_to`.
3. `POST /auth/refresh` — ротация: новый refresh, старый сразу недействителен. `POST /auth/logout` — сессия в
   Keycloak завершается, cookie удаляются всегда.

Cookie httpOnly, `SameSite=Lax`, `Secure` по окружению, **без `Domain`**: только для хоста сервиса входа. С родительским
доменом `refreshToken` (Path `/auth/`) и `accessToken` уходили бы на любой поддомен проекта, и любое приложение получило
бы сессию человека; поэтому `Cookies:Domain` убран, а заданный вручную — ошибка старта. SSO приложений — через сессию
Keycloak: каждое приложение входит само (PKCE) и носит токен в заголовке. `refresh` и `logout` только POST.
Сервисы проекта читают токен из заголовка; чтение cookie `accessToken` включается явной
настройкой (у сервиса входа). Тот же сценарий для страницы стороннего приложения — модуль `/sdk/platform-login.js`.

## Мгновенный отзыв и умный рефреш

Подпись и срок JWT проверяются локально, поэтому без дополнительной проверки отозванный токен жил бы до 15 минут
([ADR 0004](adr/0004-instant-revocation-redis.md)). Любое действие, снимающее доступ, ставит отметку в Redis; хук
`OnTokenValidated` из `Shared/Authentication` проверяет её у каждого запроса.

| Отметка | Когда | Что отклоняется |
|---|---|---|
| `auth:revoked:session:{sid}` | выход, завершение сессии, back-channel logout, блокировка, «выйти везде» | все токены сессии |
| `auth:revoked:user:{sub}` = T | блокировка, «выйти везде» | выданные раньше T (для токенов без sid) |
| `auth:revoked:app:{azp}:{sub}` = T | закрыт доступ к приложению | токены этого приложения |
| `auth:changed:user:{sub}` = версия | выданы или сняты роли | токены с меньшим `access_version` |
| `auth:changed:mode:{клиент}:{роль}` = версия | изменён состав роли | токены режима с меньшим `mode_version` |

Отметки живут 16 минут (дольше токена). Проверка идёт через Redis с коротким кэшем в памяти (2 с); экземпляр,
поставивший отметку, сбрасывает свой кэш сразу, остальные узнают за время кэша.

Отозванный токен (блокировка, сессия) получает обычный 401. Изменение доступа (роли, состав роли) — 401 с
`error_description="access_changed"`: клиент делает `POST /auth/refresh`, получает новый токен и `changes`
(что добавилось и убралось) и повторяет запрос без перелогина. **Версии, а не время**: `iat` в секундах, и токен той
же секунды прошёл бы проверку. Порядок записи — сначала Keycloak, потом Redis.

Back-channel logout: Keycloak сообщает сервису о сессиях, завершённых у него (кабинет, консоль); сервис проверяет
подпись `logout_token` и ставит отметку на сессию.

## Доступ к приложению

Встроенного «закрыть одно приложение» в Keycloak нет — завершается только сессия целиком. Поэтому: роль
`access-denied` у клиента приложения, исполнитель политики клиентов `platform-app-access` (не выдаёт и не обновляет
токены; ловит и вход по паролю, `RESOURCE_OWNER_PASSWORD_CREDENTIALS_RESPONSE`) и последний шаг сценария входа
`platform-app-access-check` со страницей «Доступ закрыт». Для приложения, у которого токены выдаёт другой клиент входа,
атрибут клиента `platform.app` указывает, у какого приложения смотреть `access-denied`.

## Админка: два уровня

Сервис вызывает Admin API Keycloak от служебной учётки клиента `*-bff` — браузеру Admin API недоступен. Права учётки
минимальные: `view-users`, `manage-users`, `view-events`, `query-clients`, точечные FGAP v2 (`view`, `map-roles`,
`map-roles-composite`, `manage`) только на клиенты приложений, `manage-branding`, `manage-sign-in`. `view-clients`
целиком не выдаётся: открывает секреты всех клиентов.

- **Админ проекта** — права режима `admin` в токене; действует на все приложения, видит всех людей.
- **Админ приложения** — права управления среди ролей *в самом приложении*; управляет только его ролями и доступом.
  В приложение сервиса входа так не войти: там действуют только права режима из токена, иначе админ в режиме
  покупателя обошёл бы режим.
- Менеджер работает только с покупателями; с собой нельзя блокировать, менять роль, закрывать доступ; выдать роль с
  управлением ролями — только после недавнего входа (5 минут, `auth_time`, `/auth/login?reauth=true`).
- Роль выдаётся и снимается только в пределах собственных прав (`UserRolesHandler.WithinOwnRightsAsync`): права
  меняемых ролей должны быть у самого меняющего; исключение — `roles.manage` (токен или роль в приложении). Права —
  из токена в приложении сервиса, из действующих ролей — в другом приложении. Тем же правилом (`OwnRights`) ограничены ключи
  сервисов (`ServiceKeysHandler.WithinOwnRightsAsync`): выдать, изменить или перевыпустить ключ можно в пределах своих прав,
  `service.users.read`/`service.access.check` сводятся к `users.view`, `service.catalog.declare` — к `roles.manage`.
- Журнал действий — таблица `auth.audit_entries` («по возможности»: сбой базы не отменяет действие). Входы — события
  Keycloak, хранятся 30 дней.

## Сервис — сервису: ключи

Ключ = confidential-клиент Keycloak `service-{код}` со служебной учёткой ([ADR 0005](adr/0005-service-keys.md)).
Токен — `client_credentials`; в нём только права ключа и `client_id`. Выдача — через client registration API
по разрешению техника (initial access token), поэтому у сервиса входа нет права управлять всеми клиентами; токен
управления своим клиентом хранится в базе, зашифрован DataProtection. Перевыпуск: срочный (старое перестаёт
действовать сразу) или плановый `keepTokens`; сервис перечитывает секрет из файла. Отзыв: сначала гасятся выданные
токены, потом удаляется клиент. Приложение объявляет свои права и роли при старте ключом (`PUT /auth/services/catalog`,
право `service.catalog.declare`).

## Коды и способы входа

([ADR 0009](adr/0009-sign-in-methods-chosen-by-person.md), [ADR 0010](adr/0010-codes-call-before-sms.md))

- Вход по коду — собственный аутентификатор плагина: код на телефон звонком-сбросом (4 цифры), SMS запасным путём,
  код на почту. Два шага: логин, затем способ; незнакомый логин неотличим от известного.
- Защита от накрутки: пауза, лимиты на номер, IP и диапазон, страны, капча, дневной бюджет проекта (исчерпание
  выключает только SMS), письма админам при 80 % и 100 %, метрики. Счётчики — в общем хранилище Keycloak
  (`SingleUseObjectProvider`), не атомарны.
- Человек выключает способы входа в кабинете (`disabled_sign_in_methods`); без ключа доступа или приложения-
  аутентификатора пароль и телефон не выключить, хотя бы один способ остаётся. Проект задаёт рамки (`platform.sign-in.*`),
  переходный период и обязательную 2FA. Настройки проекта — атрибуты realm (`platform.codes.*`, `platform.sign-in.*`),
  доступ к ним — ресурсы realm `platform-codes`, `platform-sign-in`.
- Внешний вход (Яндекс ID, Госуслуги/ЕСИА) — свои провайдеры в плагине; привязка к существующему аккаунту — паролем
  (`platform-link-password`). `syncMode: IMPORT`: данные после первого входа не обновляются.
- Телефония и капча — за интерфейсами; на стенде — заглушка `idp-stub`.

## Оформление

Название, логотип, акцент и тема проекта и приложения хранятся в Keycloak (realm и клиенты); их читают страницы входа,
письма и кабинет. Менять их можно только через плагин `platform-branding` служебной учёткой с ролью `manage-branding`.
Ключ приложения в запросе входа (`/auth/login?app={clientId}`) выбирает оформление приложения поверх проекта.

## Перенос пользователей с BCrypt

([ADR 0007](adr/0007-bcrypt-migration.md)) Разовый `partialImport` с хэшем (`credentialData.algorithm = "bcrypt"`)
через временный клиент `legacy-import` (`manage-realm`; только импорт сохраняет Id). Плагин проверяет BCrypt
(`PasswordHashProvider`, BouncyCastle из Keycloak, первые 72 байта), при первом верном входе Keycloak
перехеширует пароль в argon2. Id сохраняются, чтобы ссылки других сервисов не ломались.

## Инфраструктура

CI на каждый PR (сборка с анализаторами, тесты, админка, тема, плагин, уязвимые пакеты, gitleaks, модель EF против
миграций); живые проверки стенда и Kubernetes — ночью и на тег; релиз тегом `vX.Y.Z` — образы в GHCR, пакеты в GitHub
Packages, версия одна на всё (`scripts/package/check-version.sh`). Секреты — Infisical ([ADR 0011](adr/0011-secrets-infisical.md)),
миграции — EF вперёд и нумерованные миграции realm ([ADR 0012](adr/0012-realm-migrations.md)), Kubernetes — Helm
([ADR 0013](adr/0013-release-ghcr-helm.md)). Порядок развёртывания: мигратор базы → раскатка → мигратор realm.
