# Миграции: база сервиса, настройки проектов, обновление Keycloak

При развёртывании новой версии меняются три вещи, и у каждой — свой мигратор или свой порядок:

| Что | Кто мигрирует | Где записано, что применено |
|---|---|---|
| База сервиса (журнал, ключи сервисов, устройства) | `efbundle` из образа сервиса — контейнер `auth-migrator` | таблица `__EFMigrationsHistory` |
| Настройки проектов (realm): действия, клиенты, роли, права, CSP | `migrate-realms.py` — контейнер `realm-migrator` (`auth-realm-migrator` в `deploy/compose.yaml`) | атрибут realm `platform.realmVersion` |
| База Keycloak | сам Keycloak при старте новой версии | его таблицы (`databasechangelog`) |

Оба мигратора отрабатывают и завершаются при каждом `docker compose up`; сервис стартует только после их успеха
(`depends_on: service_completed_successfully`). Повторный запуск ничего не меняет. В Kubernetes миграторы — Job-хуки
Helm: база сервиса до раскатки, настройки проектов после нового Keycloak ([kubernetes.md](kubernetes.md#миграторы)).

## Порядок развёртывания

1. **Резервные копии обеих баз** — сервиса и Keycloak (ниже). Откатить миграцию нечем, кроме копии.
2. Новая версия: `AUTH_VERSION` в env-файле (песочница — `git pull`).
3. `docker compose up -d --wait` (песочница — `--build`): Keycloak обновляет свою базу, `auth-migrator` — базу
   сервиса, `realm-migrator` (после Keycloak) — настройки всех проектов, затем стартует сервис.
4. Логи миграторов — что применено: `docker compose logs auth-migrator auth-realm-migrator` (песочница —
   `auth-migrator realm-migrator`). Мигратор упал — сервис не стартует; причина — в его логе. Исправить и снова
   `docker compose up -d --wait`: применённые миграции не повторяются.
5. Если миграция realm дала админам новое право — им войти в админку заново (мигратор пишет об этом).

### Резервные копии

База сервиса (журнал, ключи сервисов, устройства) и база Keycloak (проекты, люди, сессии) хранят всё, поэтому копии снимаются по расписанию — обе сразу, парой.
Один скрипт [`deploy/backup/backup.sh`](../deploy/backup/backup.sh) работает везде: его запускает CronJob чарта, сервис `auth-backup` в Compose и ручной запуск.

**Что получается.** За запуск — пара файлов с общей меткой времени (UTC): `auth-service-<метка>.dump` и `keycloak-<метка>.dump` (формат custom, `pg_restore`)
и рядом `.sha256`. Копию сначала пишут во временный файл, проверяют (`pg_restore --list`), считают сумму и только потом переименовывают: недописанного файла
под настоящим именем не бывает. Сбой на второй базе убирает и готовую копию первой: пара целая или никакой. Права — `0600`: в копиях хэши паролей, телефоны
и адреса почты людей. Копия Keycloak восстанавливается **только вместе с копией сервиса той же метки**: люди и сессии — в Keycloak, журнал и ключи сервисов — в базе сервиса.

**Срок хранения.** `BACKUP_RETENTION_DAYS` (14 по умолчанию): копии старше удаляются, но `BACKUP_KEEP_MIN` (3) самых свежих каждой базы остаются всегда — если копии
перестали получаться, срок не вычистит последние рабочие. Удаление идёт только после того, как новая пара готова. Файл `last-success` хранит время последней удачной копии.

**Docker Compose** (`deploy/compose.yaml`; копии — в томе `auth_backups`):

```bash
docker compose --profile backup up -d        # расписание — AUTH_BACKUP_SCHEDULE (cron, по умолчанию 0 3 * * *, время контейнера — UTC)
docker compose exec auth-backup sh /backup.sh   # копия прямо сейчас
docker compose cp auth-backup:/backups/. ./backups   # достать копии
```

Срок и расписание — `AUTH_BACKUP_SCHEDULE`, `AUTH_BACKUP_RETENTION_DAYS`, `AUTH_BACKUP_KEEP_MIN` ([`deploy/.env.example`](../deploy/.env.example)); со своим Postgres проекта — `AUTH_BACKUP_DB_HOST`
и `AUTH_BACKUP_KEYCLOAK_DB_HOST`. Контейнер здоров, пока последняя удачная копия моложе 26 часов (`docker compose ps`; первые сутки — период разгона): подключите это к своему мониторингу.

**Kubernetes** (чарт, `backup.enabled: true`): CronJob `<релиз>-backup` по `backup.schedule`, копии — на томе (PVC `<релиз>-backups`, 10 Gi; свой — `backup.persistence.existingClaim`);
том не удаляется при `helm uninstall`. Если класс хранения привязывает том только к первому поду (`WaitForFirstConsumer`: kind, EBS, многие облака), `helm install --wait` не дождётся своего PVC — создайте том заранее и укажите его в `backup.persistence.existingClaim`. Запуск вручную: `kubectl create job --from=cronjob/<релиз>-backup backup-now`. Упавшую копию видно по состоянию Job (`kubectl get jobs`;
оповещение — по метрике kube-state-metrics `kube_job_status_failed{job_name=~".*-backup-.*"}`).

**Две базы снимаются одна за другой**, а не в один момент: запись между ними окажется только в одной (например, ключ сервиса: строка в базе сервиса и клиент в Keycloak). Снимайте в тихое время, а после восстановления проверьте список ключей сервисов в админке. Версия `pg_dump` (образ `postgres:17-alpine`) не должна быть ниже версии сервера; для внешней базы с обязательным TLS — `AUTH_BACKUP_PGSSLMODE` (Compose) или `backup.sslMode` (чарт). Срок хранения считается сутками от времени изменения файла: копия живёт до `retentionDays` полных суток, самые свежие `keepMin` остаются всегда.

**Копия на другом хосте обязательна.** Том рядом с базами не спасает от потери диска или кластера: синхронизируйте каталог копий с хранилищем вне машины (rclone, `aws s3 sync`,
снимки тома облака) и шифруйте его — в копиях персональные данные. Скрипт копий этого не делает: у каждого проекта своё хранилище.

**Восстановление в Compose** (`scripts/backup/restore.sh`; песочница — `--stand`, поставка — `--deploy`):

```bash
scripts/backup/restore.sh --dir ./backups --deploy            # покажет, какая пара выбрана, и попросит --yes
scripts/backup/restore.sh --dir ./backups --stamp 20261123T030000Z --deploy --yes
```

Скрипт проверяет суммы (повреждённая или неполная пара отклоняется до остановки сервисов), останавливает Keycloak и сервис, **стирает схемы обеих баз** и разворачивает копию
(`pg_restore`; на пустую базу после потери тома — тот же путь), запускает Keycloak и сервис и ждёт готовности. Redis не копируется: отзыв токенов между копией и сбоем пропадает
(токены живут до 15 минут). Всё, что записано в базы после копии, теряется: журнал входов за это время, выданные ключи сервисов, новые люди.

**Восстановление в Kubernetes** (те же шаги руками; сервис и Keycloak — `kubectl scale deploy/<релиз>-service deploy/<релиз>-keycloak --replicas=0`):

```bash
# копии — в под с psql и pg_restore (образ postgres:17-alpine) и доступом к базам; пароли — из Secret (PGPASSWORD=… в окружении пода)
kubectl cp ./backups/auth-service-<метка>.dump <под>:/tmp/ && kubectl cp ./backups/keycloak-<метка>.dump <под>:/tmp/
# в поде, для каждой базы (auth_service и keycloak: свой хост, пользователь и файл): стереть схемы и развернуть копию
psql -h <хост> -U <пользователь> -d <база> -v ON_ERROR_STOP=1 -c "
  DO \$\$ DECLARE s text; BEGIN
    FOR s IN SELECT nspname FROM pg_namespace WHERE nspname NOT LIKE 'pg\\_%' AND nspname <> 'information_schema' LOOP
      EXECUTE format('DROP SCHEMA %I CASCADE', s);
    END LOOP;
    CREATE SCHEMA public;
  END \$\$;"
pg_restore --single-transaction --exit-on-error --no-owner --no-privileges -h <хост> -U <пользователь> -d <база> /tmp/<файл>.dump
# затем вернуть реплики: kubectl scale … --replicas=2
```

Тот же блок стирает **все** схемы базы (в базе сервиса это `auth` и `public`, в Keycloak — `public`), как `restore.sh`. Если упало на второй базе, сервисы остаются остановленными, а первая база уже заменена:
повторите шаги для второй базы с той же меткой.

Со своим Postgres проекта (управляемая база облака) восстановление — его средствами (снимок на момент времени), если он есть; наши копии — вторая линия.

**Проверка, что копии годятся.** Копия, из которой ни разу не восстанавливались, — не копия. `scripts/keycloak/check-backup.sh` проходит весь путь на стенде: выдаёт ключ сервиса,
снимает копию настоящим скриптом, выдаёт второй ключ, «теряет» обе базы вместе с томами, восстанавливает и проверяет, что первый ключ на месте и по его секрету Keycloak выдаёт
токен, второго нет (вернулось состояние на момент копии), затем прогоняет `check-stand.sh`. Это идёт в ночном прогоне «Стенд» и раз в месяц отдельно
([`backup-restore.yml`](../.github/workflows/backup-restore.yml), 1-го числа; упало — письмо GitHub). Перед обновлением версии с миграциями ([release.md](release.md)) сделайте копию вручную и
убедитесь, что она свежая: `last-success`.

## База сервиса

Миграции EF Core — `src/AuthService.Infrastructure.Postgres/Migrations`, в образ сервиса попадают как `efbundle`.

- **Новая миграция** — после правки сущностей:
  `dotnet ef migrations add <Название> --project src/AuthService.Infrastructure.Postgres --startup-project src/AuthService.Infrastructure.Postgres`.
- **Модель не разошлась с миграциями** — `scripts/db/check-model.sh` (`dotnet ef migrations has-pending-model-changes`),
  запускается в CI: правка сущностей без миграции — красная сборка.
- **Только вперёд.** Применённую миграцию не правят и не удаляют; откат — новой миграцией, которая возвращает как
  было (`Down` в бою не запускается). Данные испорчены — восстановление из копии.
- **Совместимость со старой версией.** Пока идёт развёртывание (и при откате образа), со схемой работает и прежняя
  версия сервиса. Удалить или переименовать колонку — в две версии: сначала код перестаёт её читать, следующей версией —
  миграция удаляет. Новая колонка — со значением по умолчанию или допускает `NULL`.

## Настройки проектов (realm)

Realm импортируется из JSON только в пустую базу Keycloak, поэтому изменения шаблона
(`infra/keycloak/realm/sandbox-realm.json`) получают только новые проекты. Проектам, созданным раньше, — нумерованные
миграции `scripts/project/realm-migrations/NNNN-коротко.py`:

| № | Что | Было |
|---|---|---|
| `0001-stage-6b` | действия кабинета (смена почты — после письма), «вернуться» — в кабинет, оформление: роль `manage-branding` и право `branding.manage` | `upgrade-6b.py` |
| `0002-stage-10` | смена номера, предложение ключа, настройки входа: роль `manage-sign-in` и право `sign-in.manage`, капча в CSP | `upgrade-10.py` |
| `0003-reset-password-phone` | сброс пароля: сценарий `platform reset credentials` с серверным приведением номера (#57) | — |
| `0004-close-account-console` | кабинет Keycloak закрыт: клиенты `account` и `account-console` выключены (только свой кабинет `/account/`) | — |

**Как работает.** Мигратор (`scripts/project/migrate-realms.py`) проходит по всем realm Keycloak. Проект — realm с
клиентом `auth-api` (в песочнице `sandbox-api`); остальные и `master` не трогаются. Версия проекта — атрибут realm
`platform.realmVersion`; нет атрибута — проект старше миграций (версия 0). Недостающие миграции применяются по порядку,
после каждой версия записывается: прервался на третьей — две первые не повторятся. Новые проекты (`new-project.py`)
получают последнюю версию сразу, realm песочницы — из JSON. Версия realm новее мигратора (развернули старую версию
образа) — проект пропускается, не ошибка. Один проект не обновился — остальные обновляются, мигратор завершается с
кодом 1, сервис не стартует.

```bash
scripts/project/migrate-realms.py --status        # версии проектов, ничего не меняя
scripts/project/migrate-realms.py                 # вручную — то же, что контейнер при развёртывании
scripts/project/migrate-realms.py demo-shop       # только эти проекты
```

Контейнер берёт токен мастер-админки сам (`KC_ADMIN_DIRECT=1`: пароль `KEYCLOAK_ADMIN_PASSWORD`, адрес Keycloak в сети
Docker — `KC`); с машины — как остальные скрипты (`scripts/keycloak/master-token.sh`).

**Новая миграция** — когда меняется шаблон realm так, что старым проектам нужно то же (действие, клиент, маппер, роль,
право, сценарий входа):

1. Файл `scripts/project/realm-migrations/NNNN-коротко.py` со следующим номером: строка документации (что и зачем) и
   `apply(admin)` → строка-итог для лога (`admin` — `keycloak_admin.Admin` проекта). Готовые шаги — `enable-*.py`
   (`load_script`), как в `0002-stage-10`.
2. То же изменение — в `sandbox-realm.json`, и там же `attributes."platform.realmVersion"` — новый номер.
3. Проверка — `scripts/keycloak/check-realm-migrations.sh`: realm песочницы откатывается к виду «до 6б», контейнер
   мигратора применяет все миграции, повторный запуск ничего не меняет. Новую миграцию — добавить в откат и в итоговую
   строку проверки.

**Правила.** Миграция **идемпотентна**: создаёт, если нет (`409` — уже есть), включает, если выключено, — её можно
применить к проекту, где это уже сделано руками или шаблоном. Применённую миграцию не правят (её не применят
повторно): исправление — следующей. Не трогает то, что у каждого проекта своё: название, оформление, ключи Госуслуг и
Яндекс ID (`enable-external-login.py`), приложения проекта. Свои значения проекта не затирает (как CSP в `0002`).
Атрибуты realm — только поверх текущих: `PUT` realm с `attributes` заменяет их все, и не перечисленные (оформление,
настройки входа и кодов, версия настроек) пропадают — прочитать, дополнить, записать (`set_version` в миграторе).

## Обновление Keycloak

Плагин и тема собраны под конкретную версию Keycloak (26.4.7; [ADR 0006](tech/adr/0006-keycloak-plugins.md)): часть его SPI
внутренняя, совместимость между версиями не обещана. Порядок перехода:

1. **Версия** — в двух местах вместе: `FROM quay.io/keycloak/keycloak:<версия>` в `infra/keycloak/Dockerfile` и
   `keycloak.version` в `infra/keycloak/providers/code-login/pom.xml`; тег образа стенда в `compose.yaml`.
2. **Сборка и тесты плагина** — `docker compose build keycloak`: Maven собирает плагин под новую версию и прогоняет его
   тесты (упал тест — упала сборка), Keycloakify — тему. Ошибки компиляции — изменения SPI, смотреть заметки к выпуску
   (migration guide) Keycloak.
3. **Стенд с чистой базой** — `docker compose down -v && docker compose up -d --build --wait`, все проверки: `check-6b.sh`,
   `check-10.sh`, `check-realm-migrations.sh` и остальные `check-*.sh` ([getting-started.md](getting-started.md#проверки)).
4. **Стенд со старой базой** — так пойдёт бой: поднять стенд на прежней версии, затем новую без `down -v`; Keycloak
   мигрирует свою базу при старте, проверки — снова.
5. **Бой** — резервная копия базы Keycloak (и сервиса), затем развёртывание по порядку выше. Миграция базы Keycloak
   необратима: откат образа на старую версию на новой базе не работает — только восстановление из копии.
